# 공부 목표: 운영·성능과 보안

> 상태: 시작 전 · 작성일: 2026-09-09 · 목표 수준: Java·Spring 미들급 개발자의 독립적인 구현·검증·문제 해결

## 학습 목적

배포된 기능의 상태를 관찰하고 지연·오류의 원인을 좁히며, 접근 권한과 배포 변경의 안전성을 검증한다.

**학습 우선순위:** 기본 API가 동작하면 관찰 수단을 먼저 추가한다. 진단 실습은 다른 주제의 실패 실험과 연결한다.

## 학습 환경

- Java / Spring Boot 버전: 미정
- DB / 데이터 접근 기술: 미정
- 실습 코드 위치: 미정

현재 프로젝트의 기술과 버전을 적은 뒤 시작한다. 확인하지 않은 동작은 가정으로 표시하고 실습으로 검증한다.

## 핵심 개념별 목표

- [ ] **로그·지표·추적**: 로그는 개별 사건, 지표는 오류율·처리량 같은 수치, 추적은 요청이 여러 호출을 거치는 경로다. 요청 식별자로 관련 기록을 연결한다.
- [ ] **성능 지표**: 처리량, 오류율, 지연시간 분포를 읽는다. p95는 요청의 95%가 그 이하 시간에 처리됐다는 뜻이며 평균값과 함께 해석한다.
- [ ] **병목과 자원 한도**: CPU 작업, 메모리와 GC, 스레드 대기, DB 연결 대기, 외부 API 지연을 구분한다. 풀 크기를 늘리는 선택의 효과와 비용을 검증한다.
- [ ] **배포와 복구**: 상태 점검, 트래픽 수신 준비 상태, 진행 중 요청을 마치는 종료, 롤백을 이해한다. 이전·새 애플리케이션 버전이 공존할 때 DB 변경의 호환성을 검토한다.
- [ ] **인증과 인가**: 인증은 사용자 신원 확인이며 인가는 자원과 작업에 대한 권한 확인이다. 로그인 여부와 특정 주문의 소유권 검사를 구분한다.
- [ ] **입력·비밀정보 보호**: 입력 검증, SQL 매개변수 바인딩, 비밀정보의 설정 분리와 로그 마스킹을 적용한다. 인증 방식에 따라 CSRF와 CORS의 목적 및 적용 조건을 구분한다.

## 실습 과제

1. Spring Boot의 운영 상태 확인 기능인 Actuator와 지표 수집을 연결하고, 요청 수·오류율·지연시간·DB 연결 상태를 관찰한다.
2. 로컬 환경에서 느린 SQL, 외부 응답 지연, DB 연결 부족을 각각 만들고 지표와 로그로 원인을 구분한다. 동일한 부하 조건으로 개선 전후를 비교한다.
3. 사용자 A가 사용자 B의 주문을 조회·변경할 수 없는지 테스트한다. 운영 진단 기능의 접근 권한과 로그의 비밀정보 노출도 점검한다.
4. 진행 중 요청이 있는 상태의 종료와 이전 버전으로의 복구를 실험하고, DB 변경 때문에 복구가 제한되는 조건을 기록한다.

## 스스로 설명할 질문

- 평균 응답 시간은 정상인데 일부 사용자가 느리다면 어떤 지표를 확인하는가?
- CPU 사용률이 낮은데 요청이 쌓일 때 다음으로 확인할 자원은 무엇인가?
- 로그인한 사용자의 다른 사람 주문 접근을 어디서 차단하는가?
- 애플리케이션을 이전 버전으로 돌리는 것만으로 복구되지 않는 변경은 무엇인가?

## 완료 기준

- [ ] 요청 하나의 처리 경로를 로그와 식별자로 추적한다.
- [ ] 서로 다른 지연 원인 두 가지 이상을 측정 근거로 구분한다.
- [ ] 자원 소유권 검사와 민감정보 보호를 검증한다.
- [ ] 배포 실패 시 복구 절차와 DB 변경의 호환성 제약을 설명한다.
- [ ] 실패 또는 경계 조건을 최소 하나 직접 재현하고 결과를 기록한다.
- [ ] 선택한 방법과 대안의 비용을 비교하고 코드·테스트·로그 등 검증 근거를 연결한다.

개념 체크는 자신의 말로 설명하고 예제에서 확인했을 때 표시한다. 문서나 강의를 읽은 것만으로 완료 처리하지 않는다.
