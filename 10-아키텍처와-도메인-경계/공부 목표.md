# 공부 목표: 아키텍처와 도메인 경계

> 상태: 시작 전 · 작성일: 2026-09-09 · 목표 수준: Java·Spring 미들급 개발자의 독립적인 구현·검증·문제 해결

## 학습 목적

기능을 어느 계층·모듈에 둘지 판단하고, 요구사항이 바뀔 때 변경 범위를 예측 가능한 구조로 유지한다. 6번 주제가 "테스트하기 쉬운 코드"를 다룬다면, 이 주제는 그보다 상위의 판단인 "이 로직은 어디에 속해야 하는가"를 다룬다.

**학습 우선순위:** 트랜잭션(3번)과 테스트·설계(6번) 학습 후 진행한다. 서비스 클래스가 계속 비대해지거나 기능 하나를 바꿀 때 여러 곳을 함께 고쳐야 하는 문제를 겪고 있다면 우선순위를 높인다.

## 학습 환경

- Java / Spring Boot 버전: 미정
- DB / 데이터 접근 기술: 미정
- 실습 코드 위치: 미정

현재 프로젝트의 기술과 버전을 적은 뒤 시작한다. 확인하지 않은 동작은 가정으로 표시하고 실습으로 검증한다.

## 핵심 개념별 목표

- [ ] **계층형 아키텍처의 책임 분리**: Controller·Service·Repository 각 계층이 알아야 할 것과 몰라야 할 것을 구분한다.
- [ ] **도메인 로직과 인프라 로직 분리**: 비즈니스 규칙이 특정 DB·프레임워크 API에 묶이는 문제와, 포트/어댑터 방식으로 분리하는 방법을 이해한다.
- [ ] **응집도와 결합도**: 하나의 클래스가 서로 다른 이유로 여러 번 바뀌는 문제(단일 책임 원칙 위반)를 실제 코드에서 판단한다.
- [ ] **도메인 경계 나누기**: 하나의 큰 도메인을 어떤 기준(같은 트랜잭션·불변식 안에서 함께 지켜져야 하는 단위)으로 나눌지 판단한다.
- [ ] **모듈·패키지 구조와 순환 의존성**: 패키지 간 의존 방향을 강제하는 방법과 순환 의존이 생기는 원인을 설명한다.
- [ ] **레이어드 vs 포트/어댑터(헥사고날) 아키텍처**: 각 방식의 장단점과, 서비스 복잡도·팀 규모에 따른 선택 기준을 비교한다.

## 실습 과제

1. 기존 서비스 클래스 하나를 골라 책임을 나열하고, 서로 다른 이유로 바뀌는 부분을 분리한다.
2. 도메인 로직에서 특정 ORM·프레임워크 API 의존을 제거하고, Spring 컨텍스트 없이 순수 자바 객체로 테스트 가능하게 리팩터링한다.
3. 패키지 의존 방향을 검사하는 도구(예: ArchUnit)로 규칙을 정의하고, 규칙을 위반하는 기존 코드가 있는지 찾는다.
4. 작은 도메인 하나를 레이어드 방식과 포트/어댑터 방식으로 각각 구현하고, DB를 교체하는 시나리오에서 영향 범위를 비교한다.

## 스스로 설명할 질문

- Service 클래스가 지나치게 커졌다면 어떤 기준으로 나눌 것인가?
- 도메인 로직 테스트에 Spring 컨텍스트 구동이 필요하다면 무엇이 잘못된 설계인가?
- 두 기능이 같은 트랜잭션 경계 안에 있어야 하는지는 어떤 기준으로 판단하는가?

## 완료 기준

- [ ] 계층별 책임을 실제 코드에서 구분하고 위반 사례를 지적한다.
- [ ] 도메인 로직과 인프라 의존을 분리한 전후 코드를 비교해 설명한다.
- [ ] 순환 의존이나 계층 위반 사례를 하나 이상 찾아 해소한 근거를 남긴다.
- [ ] 실패 또는 경계 조건을 최소 하나 직접 재현하고 결과를 기록한다.
- [ ] 선택한 방법과 대안의 비용을 비교하고 코드·테스트·로그 등 검증 근거를 연결한다.

개념 체크는 자신의 말로 설명하고 예제에서 확인했을 때 표시한다. 문서나 강의를 읽은 것만으로 완료 처리하지 않는다.
