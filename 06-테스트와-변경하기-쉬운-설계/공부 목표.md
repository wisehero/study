# 공부 목표: 테스트와 변경하기 쉬운 설계

> 상태: 시작 전 · 작성일: 2026-09-09 · 목표 수준: Java·Spring 미들급 개발자의 독립적인 구현·검증·문제 해결

## 학습 목적

업무 규칙과 외부 의존성을 구분하고, 중요한 동작을 검증하는 테스트를 통해 변경의 영향과 위험을 통제한다.

**학습 우선순위:** 모든 주제의 실습과 병행한다. 테스트를 학습 마지막 단계로 미루지 않는다.

## 학습 환경

- Java / Spring Boot 버전: 미정
- DB / 데이터 접근 기술: 미정
- 실습 코드 위치: 미정

현재 프로젝트의 기술과 버전을 적은 뒤 시작한다. 확인하지 않은 동작은 가정으로 표시하고 실습으로 검증한다.

## 핵심 개념별 목표

- [ ] **테스트 범위**: 단위 테스트는 작은 범위의 업무 규칙을, 통합 테스트는 Spring 설정·DB·외부 경계의 연결 동작을 검증한다. 각 범위를 선택한 이유를 설명한다.
- [ ] **검증 대상**: 구현 순서보다 외부에서 관찰 가능한 결과와 업무 규칙을 검증한다. 정상·경계·예외·동시 실행 사례를 구분한다.
- [ ] **테스트 대역**: 외부 의존성을 대신하는 가짜 객체의 역할과 한계를 이해한다. 실제 DB 제약과 롤백을 검증할 때 필요한 실행 환경을 선택한다.
- [ ] **책임과 의존성**: 업무 판단, 데이터 저장, 외부 API 호출의 책임을 구분한다. 함께 변경되는 코드와 따로 변경되는 코드를 근거로 경계를 정한다.
- [ ] **도메인 상태**: 주문 상태처럼 업무적으로 허용되는 상태와 전이를 명시하고 잘못된 조합을 방지한다.
- [ ] **리팩터링과 리뷰**: 관찰 가능한 동작을 유지하면서 구조를 바꾸고, 작은 변경 단위와 검증 근거로 리뷰를 준비한다. 추상화가 추가하는 복잡성도 비교한다.

## 실습 과제

1. 할인 계산 또는 주문 상태 전환을 외부 시스템 없이 테스트할 수 있는 구조로 분리한다.
2. 재고 부족, 중복 주문, 외부 호출 실패를 검증하는 테스트를 작성한다. DB 제약·롤백 테스트에는 실제 사용하는 DB와 호환되는 환경을 사용한다.
3. 실제 커밋 이후의 동작을 검증하는 테스트를 만들고, 테스트 자체의 트랜잭션과 자동 롤백이 결과를 가리지 않는지 확인한다.
4. 결제 수단을 하나 추가하고 변경된 파일의 범위와 기존 동작을 보호하는 테스트를 기록한다.

## 스스로 설명할 질문

- 테스트가 모두 통과해도 실제 DB에서 실패할 수 있는 이유는 무엇인가?
- 새로운 요구사항이 생겼을 때 어떤 책임을 어디에 추가해야 하는가?
- 이번 추상화가 줄이는 변경 비용과 추가하는 복잡성은 무엇인가?

## 완료 기준

- [ ] 중요한 업무 규칙마다 정상과 실패 사례를 검증한다.
- [ ] 가짜 객체로 검증할 범위와 실제 연동이 필요한 범위를 설명한다.
- [ ] 기존 동작을 유지하는 구조 개선 또는 기능 확장을 수행하고 리뷰 가능한 근거를 남긴다.
- [ ] 실패 또는 경계 조건을 최소 하나 직접 재현하고 결과를 기록한다.
- [ ] 선택한 방법과 대안의 비용을 비교하고 코드·테스트·로그 등 검증 근거를 연결한다.

개념 체크는 자신의 말로 설명하고 예제에서 확인했을 때 표시한다. 문서나 강의를 읽은 것만으로 완료 처리하지 않는다.
