# 공부 목표: HTTP·외부 API와 실패 처리

> 상태: 시작 전 · 작성일: 2026-09-09 · 목표 수준: Java·Spring 미들급 개발자의 독립적인 구현·검증·문제 해결

## 학습 목적

외부 시스템의 지연, 응답 유실, 중복 요청을 전제로 API를 설계하고 결과가 불명확한 작업을 안전하게 복구한다.

**학습 우선순위:** 트랜잭션 기본 실습 뒤 진행한다. 결제·배송 등 외부 연동 업무가 있으면 우선순위를 높인다.

## 학습 환경

- Java / Spring Boot 버전: 미정
- DB / 데이터 접근 기술: 미정
- 실습 코드 위치: 미정

현재 프로젝트의 기술과 버전을 적은 뒤 시작한다. 확인하지 않은 동작은 가정으로 표시하고 실습으로 검증한다.

## 핵심 개념별 목표

- [ ] **HTTP 의미와 계약**: 메서드, 상태 코드, 헤더, 캐시의 기본 의미를 이해하고 요청·응답 형식과 오류 응답의 계약을 정의한다.
- [ ] **타임아웃**: 연결 대기와 응답 대기, 전체 작업 시간 제한을 구분한다. 클라이언트가 기다리기를 중단한 뒤에도 서버 작업이 완료될 수 있음을 이해한다.
- [ ] **재시도**: 일시적 오류와 영구적 오류를 구분하고 재시도 횟수·대기 시간·전체 시간 예산을 정한다. 여러 계층의 재시도가 호출 수를 증폭시키는 상황을 고려한다.
- [ ] **멱등성**: 같은 작업을 반복해도 효과가 중복되지 않는 성질이다. 멱등성 키의 범위·저장·만료, 같은 키에 다른 요청 내용이 오는 경우를 설계한다.
- [ ] **부분 실패와 복구**: 외부 결제 성공 후 내부 저장 실패처럼 시스템 간 결과가 어긋나는 상황을 모델링한다. 결과 조회, 상태 대조, 취소 등 후속 처리 기준을 정한다.
- [ ] **장애 전파 제한**: 외부 시스템이 느릴 때 우리 서비스의 스레드와 연결이 소진되지 않도록 동시 호출 수와 대기열을 제한한다. 반복 실패 시 호출을 일시 차단하는 회로 차단기의 목적을 이해한다.

## 실습 과제

1. 실제 결제 대신 로컬 가짜 결제 서버를 만들고, 성공·명시적 실패·응답 지연·처리 후 응답 유실을 각각 재현한다.
2. 주문 API에 멱등성 키를 도입하고 순차 중복과 동시 중복 요청 모두에서 주문과 결제가 중복되지 않는지 검증한다.
3. 결과 불명 상태를 별도로 저장하고 외부 거래 조회를 통해 최종 상태를 확정하는 복구 흐름을 만든다.
4. 재시도 최대 횟수와 전체 제한 시간을 검증하고 중복 효과와 호출 폭증이 없는지 확인한다.

## 스스로 설명할 질문

- 결제 요청이 타임아웃이면 결제 실패로 확정할 수 있는가?
- 같은 멱등성 키에 다른 금액이 들어오면 어떻게 응답해야 하는가?
- 외부 결제는 성공했는데 우리 DB 저장이 실패하면 어떻게 복구하는가?

## 완료 기준

- [ ] 성공·실패·결과 불명의 상태와 전이 조건을 구분한다.
- [ ] 순차 및 동시 중복 요청에서 중복 효과가 발생하지 않음을 검증한다.
- [ ] 재시도 조건과 한도를 설명하고 복구 가능한 거래 식별자를 남긴다.
- [ ] 실패 또는 경계 조건을 최소 하나 직접 재현하고 결과를 기록한다.
- [ ] 선택한 방법과 대안의 비용을 비교하고 코드·테스트·로그 등 검증 근거를 연결한다.
