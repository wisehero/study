# 첫 트랜잭션 실습 기록

검증일: 2026-09-11

## 문제와 환경

주문 저장 후 재고 부족이 발생했을 때 주문이 남는 조건을 비교했다. Java 21, Spring Boot 4.1.1, Testcontainers의 PostgreSQL 17.6에서 실제 SQL을 실행했다.

- 실습 서비스: [OrderService](../spring-lab/src/test/java/dev/study/commerce/transaction/OrderService.java)
- 검증 코드: [OrderTransactionTest](../spring-lab/src/test/java/dev/study/commerce/OrderTransactionTest.java)
- 초기 데이터: [order-transaction.sql](../spring-lab/src/test/resources/sql/order-transaction.sql)

## 재현 방법과 검증 결과

Spring Lab에서 Docker 실행 후 `./gradlew test`를 실행했다. 신규 3개와 기존 상품 API 9개, 총 12개 테스트가 실패·오류·건너뛰기 없이 통과했다.

각 테스트는 주문 0건, 상품 `CREAM`의 재고 10개로 시작한다. 서비스 트랜잭션이 종료된 뒤 별도 조회로 확인한 결과는 다음과 같다.

| 조건 | 예상 결과 | 실제 결과 |
| --- | --- | --- |
| 3개 주문 성공 | 주문 1건(수량 3), 재고 7 | 일치 |
| 11개 주문 중 재고 부족 예외 전달 | 예외 발생, 주문 0건, 재고 10 | 일치 |
| 11개 주문 중 재고 부족 예외를 잡고 반환 | 반환값 false, 주문 1건(수량 11), 재고 10 | 일치 |

테스트에 자동 롤백 트랜잭션을 걸지 않았다. 테스트 데이터 준비, 서비스 호출, 결과 조회가 서비스의 한 트랜잭션으로 묶이지 않으므로 실제 커밋·롤백 결과를 관찰한다.

## 선택한 방법과 한계

SQL 실행 순서와 예외 처리에 집중하기 위해 JdbcTemplate과 테스트 전용 테이블 두 개를 사용했다. 기존 상품 API의 테이블과 로컬 학습 데이터를 사용하지 않는다. JPA 엔티티·저장소·HTTP API로 확장하는 작업은 이번 범위에 포함하지 않았다.

원자적으로 처리해야 하는 주문·재고 작업에는 예외를 트랜잭션 밖으로 전달하는 두 번째 방식이 맞다. 세 번째 방식은 잘못된 주문이 남는 현상을 재현하기 위해 유지한 문제 예제다. 예외를 잡는 방식 자체가 항상 잘못인 것은 아니며, 이미 롤백 전용 상태인 경우의 동작은 이번 결과와 구분해야 한다.

이번 실패는 재고를 변경하기 전에 발생한다. 재고 변경 후 추가 실패, 체크 예외, 트랜잭션 전파, 동시 구매는 검증하지 않았다. 코드 실행 결과를 확인한 상태이며, 사용자가 직접 수정하고 이유를 설명하는 학습 확인은 남아 있다.
