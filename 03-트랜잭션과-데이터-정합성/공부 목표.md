# 공부 목표: 트랜잭션과 데이터 정합성

> 상태: 시작 전 · 작성일: 2026-09-09 · 목표 수준: Java·Spring 미들급 개발자의 독립적인 구현·검증·문제 해결

## 학습 목적

동시 요청과 예외가 발생해도 데이터가 업무 규칙에 맞게 유지되도록 트랜잭션 경계와 충돌 처리 방법을 설계한다.

**학습 우선순위:** 최우선 심화 주제다. Spring 프록시 기본기와 DB 기본 지식을 함께 적용한다.

## 학습 환경

- Java / Spring Boot 버전: 미정
- DB / 데이터 접근 기술: 미정
- 실습 코드 위치: 미정

현재 프로젝트의 기술과 버전을 적은 뒤 시작한다. 확인하지 않은 동작은 가정으로 표시하고 실습으로 검증한다.

## 핵심 개념별 목표

- [ ] **업무 규칙과 트랜잭션 경계**: 트랜잭션은 여러 변경을 하나의 작업 단위로 묶는 장치다. 재고 음수 금지, 주문 중복 금지처럼 항상 지켜야 할 규칙을 먼저 정의한다.
- [ ] **전파와 롤백**: REQUIRED의 기존 트랜잭션 참여와 REQUIRES_NEW의 독립 트랜잭션을 비교한다. 예외 종류, 롤백 설정, 예외를 잡는 위치에 따른 결과를 확인한다.
- [ ] **격리 수준과 동시 실행**: 격리 수준은 동시 트랜잭션이 서로의 변경을 보는 규칙이다. 읽기 결과 변화와 갱신 충돌을 실제 사용하는 DB의 동작으로 설명한다.
- [ ] **동시성 제어**: 변경 충돌을 감지하는 낙관적 락, 먼저 잠그는 비관적 락, 조건부 UPDATE, 유니크 제약의 적용 조건과 실패 처리를 비교한다.
- [ ] **데드락과 재시도**: 데드락은 서로가 가진 잠금을 기다리는 상황이다. 잠금 순서와 트랜잭션 길이의 영향을 이해하고, 재시도할 작업 범위를 정한다.
- [ ] **보장의 범위**: 일반적인 로컬 DB 트랜잭션은 외부 HTTP 호출까지 함께 롤백하지 못한다. 일반적인 스레드 기반 트랜잭션이 새 스레드로 자동 전파되지 않는다는 점을 구분한다.

## 실습 과제

1. 주문 생성과 재고 차감을 구현하고, 각 단계에 실패를 넣어 커밋·롤백 결과를 확인한다.
2. 별도 DB 연결과 트랜잭션을 사용하는 동시 구매 요청을 만들어 재고 1개를 초과 판매하는 문제를 재현한다.
3. 조건부 갱신과 낙관적 또는 비관적 락을 비교한다. 성공 수, 실패 응답, 최종 재고와 재시도 정책을 기록한다.
4. 독립된 두 트랜잭션의 잠금 순서를 다르게 하여 데드락을 재현하고, 순서 통일 또는 재시도 방안을 검증한다.

## 스스로 설명할 질문

- @Transactional만으로 동시 구매의 초과 판매를 막을 수 있는가?
- 예외를 catch하면 언제 커밋되거나 롤백되는가? 이미 롤백 전용으로 표시된 경우는 어떻게 다른가?
- 내부 작업을 REQUIRES_NEW로 분리하면 외부 작업의 실패와 어떤 관계가 생기는가?

## 완료 기준

- [ ] 업무 규칙과 원자적으로 처리해야 할 변경을 문서로 정의한다.
- [ ] 실제 DB에서 동시 요청 문제를 재현하고 해결 후 데이터와 응답을 검증한다.
- [ ] 최소 두 가지 충돌 처리 방식의 장단점과 실패 시 동작을 비교한다.
- [ ] 로컬 트랜잭션이 보장하지 못하는 외부 시스템·스레드 경계를 설명한다.
- [ ] 실패 또는 경계 조건을 최소 하나 직접 재현하고 결과를 기록한다.
- [ ] 선택한 방법과 대안의 비용을 비교하고 코드·테스트·로그 등 검증 근거를 연결한다.

개념 체크는 자신의 말로 설명하고 예제에서 확인했을 때 표시한다. 문서나 강의를 읽은 것만으로 완료 처리하지 않는다.
