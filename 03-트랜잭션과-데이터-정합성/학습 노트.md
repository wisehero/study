# 첫 실습: 주문 저장과 재고 차감의 커밋·롤백

먼저 [Spring @Transactional 기본 동작 원리](Transactional%20기본%20동작%20원리.md)에서 프록시, DB 연결, 트랜잭션 시작·종료 흐름을 확인한 뒤 실습을 읽는다.

## 목적과 핵심 결과

트랜잭션은 여러 DB 변경을 하나의 작업 단위로 묶는다. 변경을 확정하는 것을 **커밋**, 취소하는 것을 **롤백**이라고 한다. 이번 실습은 주문 저장 이후 재고가 부족할 때, 예외를 밖으로 전달하는 경우와 안에서 잡는 경우를 비교한다.

이 예제에서는 런타임 예외가 서비스 밖으로 전달되면 주문 저장도 롤백된다. 같은 예외를 서비스 안에서 잡고 `false`를 반환하면 주문 저장은 커밋된다. 실패를 뜻하는 반환값과 트랜잭션 롤백은 별개다.

## 실습 흐름

매번 상품 코드 `CREAM`의 재고 10개, 주문 0건으로 시작한다.

```text
테스트 → Spring 프록시 → OrderService → 주문 INSERT → 재고 확인 → 재고 UPDATE
                         트랜잭션 시작                              커밋 또는 롤백
```

**프록시**는 서비스 호출 앞뒤에서 트랜잭션 시작과 종료를 처리하는 Spring의 중개 객체다. 테스트가 Spring에서 전달받은 `OrderService`를 호출하므로 메서드의 `@Transactional`이 적용된다. 직접 `new OrderService(...)`로 만들면 이 호출 경로를 거치지 않는다.

| 케이스 | 요청과 처리 | 호출 결과 | 종료 후 주문 | 종료 후 재고 |
| --- | --- | --- | --- | --- |
| 1. 정상 처리 | 3개 주문, 재고 차감 성공 | 정상 반환 | 3개짜리 주문 1건 | 7개 |
| 2. 예외 전달 | 11개 주문, 재고 부족 예외 전달 | `IllegalStateException` | 0건 | 10개 |
| 3. 예외 잡기 | 11개 주문, 재고 부족 예외를 catch | `false` 반환 | 11개짜리 주문 1건 | 10개 |

2번은 이미 실행한 주문 INSERT를 취소한다. 재고는 UPDATE 전에 예외가 발생하므로 애초에 변경되지 않았다. 따라서 이 케이스만으로 변경된 재고의 복구까지 검증했다고 말할 수는 없다.

3번은 의도적인 문제 예제다. 재고가 부족한데도 주문이 남는다. 예외는 같은 서비스의 private 메서드에서 직접 발생하며, 이를 catch한 후에는 프록시까지 전달되지 않는다. DB 오류나 별도 서비스의 트랜잭션 실패도 발생하지 않아, 트랜잭션이 롤백해야 할 상태로 표시되지 않는다.

## 코드 읽는 순서와 실행

1. [OrderService](../spring-lab/src/test/java/dev/study/commerce/transaction/OrderService.java): `order`의 저장·차감 순서를 읽고 `orderWithCaughtError`의 catch와 비교한다.
2. [초기 데이터](../spring-lab/src/test/resources/sql/order-transaction.sql): 테스트용 주문·재고 테이블과 초기 재고를 확인한다.
3. [OrderTransactionTest](../spring-lab/src/test/java/dev/study/commerce/OrderTransactionTest.java): 실행 전에 각 테스트의 주문 수와 재고를 예상한다.

Spring Lab 폴더에서 Docker가 실행 중인 상태로 다음 명령을 실행한다.

```sh
./gradlew test --tests 'dev.study.commerce.OrderTransactionTest'
```

Testcontainers는 테스트용 PostgreSQL을 만들고 종료 후 정리하는 도구다. 테스트의 `@Sql`은 각 케이스 전에 초기 데이터를 준비한다. 테스트 메서드에는 `@Transactional`을 붙이지 않았으며, 서비스 호출이 끝난 뒤 DB를 다시 조회해 실제 커밋·롤백 결과를 확인한다.

`JdbcTemplate`은 SQL 실행을 돕는 Spring 도구다. SQL이 실행되는 순서를 바로 읽을 수 있도록 사용했다. 기존 앱의 DB 연결과 Spring 트랜잭션 관리에 참여하며, 이번 예제에는 JPA 엔티티나 HTTP API가 필요하지 않다. 실습 서비스와 SQL은 모두 `src/test` 아래에 있어 테스트에서만 사용한다.

## 적용 기준과 한계

- 주문과 재고 차감이 함께 성공해야 한다면, 이 예제에서는 2번처럼 재고 부족 예외를 트랜잭션 경계 밖으로 전달한다. 사용자용 오류 응답으로 바꾸는 처리는 그 경계 밖에서 할 수 있다.
- **catch하면 항상 커밋되는 것은 아니다.** DB 오류나 다른 트랜잭션 참여자의 실패로 이미 롤백 전용 상태가 됐다면 정상 반환해도 커밋할 수 없다. 별도 서비스 호출과 전파 방식은 후속 실습에서 다룬다.
- 이번 예제는 존재하는 상품에 양수 수량을 요청하는 경우를 다룬다. 상품 없음·잘못된 입력·중복 요청은 별도 범위다.
- 재고 조회와 갱신 사이의 동시 요청을 막는 처리는 없다. 세 테스트의 성공은 동시 구매의 안전성을 의미하지 않는다.

## 직접 확인할 질문

1. 2번에서 INSERT가 실행됐는데 주문이 남지 않는 이유는 무엇인가?
2. 3번은 `false`를 반환했는데 왜 주문이 남는가?
3. 3번의 catch에서 `return false`를 `throw error`로 바꾸면 테스트 결과는 어떻게 달라지는가?

실습 결과와 자신의 설명을 확인한 뒤 학습 완료 여부를 판단한다.
