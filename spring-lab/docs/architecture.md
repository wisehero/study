# 구조와 설계 선택

## 목적과 현재 범위

한 애플리케이션 안에서 도메인별 책임을 나누는 구조다. 별도 서비스나 다중 빌드 모듈을 먼저 만들지 않고, 코드와 트랜잭션 경계를 눈으로 확인할 수 있는 크기에서 시작한다. 상품 등록·조회만 실행 가능한 예제로 구현했다.

```text
dev.study.commerce
├── catalog        상품 원본 등록·조회 예제
│   ├── api        요청 검증, HTTP 응답
│   ├── application 업무 실행, 트랜잭션 경계, 응답용 데이터
│   ├── domain     상품과 상태
│   └── infrastructure JPA를 통한 저장과 조회
├── ordering       주문 실습 시작 위치
├── inventory      재고 실습 시작 위치
├── display        전시 실습 시작 위치
├── ranking        랭킹 실습 시작 위치
├── search         검색 실습 시작 위치
└── shared         인증 설정과 공통 HTTP 오류 처리
```

빈 업무 패키지에는 역할을 설명하는 `package-info.java`만 둔다. 기능 구현 시 필요한 계층을 추가한다. 비어 있는 서비스가 정상 결과를 반환하는 가짜 API는 만들지 않았다.

## 요청의 전체 흐름

상품 등록은 `AdminProductController → ProductService → ProductRepository → PostgreSQL`로 실행된다. 컨트롤러는 요청 형식을 검증하며, 서비스는 트랜잭션을 시작하고, DB는 상품 코드의 유일성과 가격의 범위를 최종 검사한다.

고객 상품 조회는 서비스에서 ACTIVE 상태를 조회 조건에 포함한다. 초안 상품의 ID를 알아도 고객 API에서는 찾을 수 없음으로 응답한다. 엔티티를 응답으로 직접 직렬화하지 않고 `ProductView`로 변환한다.

## 현재 선택과 한계

- **단순 계층형 구조:** 서비스가 Spring Data 저장소에 직접 의존하고 도메인 객체에 JPA 매핑이 있다. 처음부터 모든 계층에 인터페이스를 추가하지 않았다. 포트/어댑터 실습에서는 저장소 경계와 순수 업무 규칙을 직접 분리한다.
- **상품 코드와 가격:** 상품 코드는 대문자 영문·숫자·하이픈 1~40자이며 고유하다. 가격은 KRW 정수 금액이고 0 이상이다. 통화 변환과 할인은 구현하지 않았다.
- **상태:** DRAFT는 초안, ACTIVE는 공개·판매 중, SUSPENDED는 중지 상태다. 품절과 수량은 상품의 공개 상태와 다른 개념이며 inventory 실습에서 추가한다.
- **트랜잭션:** 변경은 서비스 메서드에서 묶는다. 조회는 읽기 전용 트랜잭션이며 JPA 세션을 응답 직렬화까지 유지하는 Open Session in View는 끈다.
- **중복:** 사전 조회만으로 중복을 막지 않는다. DB 유니크 제약을 사용하며 충돌은 409로 변환한다. 이 오류 처리는 현재 상품 예제의 최소 수준이며 제약별 세밀한 오류 코드는 확장 과제다.
- **버전:** 엔티티에 낙관적 락용 `@Version`을 준비했다. 수정 API가 없으므로 동시 수정 문제를 해결했다고 볼 수 없다. 클라이언트가 읽은 버전과 충돌 응답까지 다음 실습에서 구현한다.
- **페이지:** 0부터 시작하는 페이지와 최대 50개 크기를 사용하고 ID로 정렬한다. 여러 요청에 걸친 목록 변경에 대한 조회 시점 고정은 구현하지 않았다.
- **보안:** 로컬 관리자 계정과 HTTP Basic을 사용하고 CSRF 보호를 유지한다. 세션 쿠키는 토큰 검증에 사용한다. 사용자 가입·주문 소유권 검사는 후속 과제다.
- **DB 변경:** 기본 테이블 변경과 local 샘플 데이터를 경로로 나눴다. 기존 마이그레이션의 버전·내용을 바꾸지 않고 새 파일을 추가한다.

## 도메인 연결 원칙

상품 원본과 전시 배치는 별도 개념으로 다룬다. 다른 도메인에서 상품 JPA 엔티티나 저장소를 직접 가져오기 전에 필요한 데이터와 호출 계약을 정한다. 별도 모듈의 인터페이스, 조회 서비스, 이벤트 중 어떤 방식이 적합한지는 실습에서 비교한다.

상품 변경과 아웃박스 이벤트 기록을 도입할 때는 **같은 DB 트랜잭션에 함께 저장**하고, 커밋된 아웃박스 항목을 별도 발행자가 전달한다. 이벤트 중복·역순·유실과 읽기 모델 재구성은 아직 구현하지 않았다.

랭킹은 인기의 기준과 집계 버전을, 검색은 검색어 관련도와 검색용 데이터 갱신을 담당한다. 전시 화면은 두 결과를 소비하되 고객 공개 정책을 일관되게 적용해야 한다.

## 검증 방식

통합 테스트는 별도 PostgreSQL에서 Flyway·JPA·Spring MVC·Spring Security를 함께 실행한다. 테스트 메서드 전체에 자동 롤백 트랜잭션을 걸지 않으므로 실제 서비스의 커밋과 제약 충돌 뒤 저장 결과를 확인할 수 있다.

현재 테스트는 기초 API의 동작을 검증한다. 동시 구매, 읽기 모델 동기화, 랭킹·검색 정확성과 성능을 검증하는 테스트는 각 기능 구현과 함께 추가한다.
