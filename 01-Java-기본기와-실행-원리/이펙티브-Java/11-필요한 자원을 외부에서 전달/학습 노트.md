# 필요한 자원을 외부에서 전달

학습일: 2026-09-14 · 학습 순서 11 · 아이템 5

## 핵심 결론

객체가 사용하는 자원을 내부에서 고정하면 실행 환경을 바꾸거나 테스트하기 어렵다. 필요한 자원을 외부에서 전달받으면 같은 업무 로직을 서로 다른 환경에서 사용할 수 있다. 이를 의존성 주입이라고 한다. 의존 자원은 시계나 데이터 저장소처럼 객체가 일을 수행하는 데 필요한 대상이다.

판단에 필요한 값 하나면 충분할 때는 그 값을 전달한다. 객체가 필요할 때마다 자원을 사용해야 한다면 자원 자체를 전달한다. 이 노트는 대화에서 학습한 개념과 설명용 코드이며, 실습 코드를 추가하거나 테스트를 실행한 기록은 아니다.

## 현재 시각을 직접 읽으면 생기는 문제

기획전은 시작 시각을 포함하고 종료 시각을 제외하는 기간에 노출된다고 정한다. `Instant`는 특정 시점을 나타내는 Java 타입이다.

```java
boolean isActive(Instant start, Instant end) {
    Instant now = Instant.now();
    return !now.isBefore(start) && now.isBefore(end);
}
```

이 메서드는 호출할 때마다 실제 현재 시각을 읽는다. 따라서 테스트에서 시작 1초 전, 정확히 시작 시각, 정확히 종료 시각을 안정적으로 재현하기 어렵다. 원인은 `now`라는 변수명이 아니라 메서드가 시간의 출처를 직접 결정한다는 점이다.

## 시계 객체를 전달하는 방법

`Clock`은 현재 시각을 제공하는 Java의 시계 추상 클래스다. 운영에서는 흐르는 시계를, 테스트에서는 고정된 시계를 전달할 수 있다. 의존성 주입을 위해 반드시 직접 인터페이스를 만들 필요는 없다.

```java
class Promotion {
    private final Clock clock;

    Promotion(Clock clock) {
        this.clock = clock;
    }

    boolean isActive(Instant start, Instant end) {
        Instant now = Instant.now(clock);
        return !now.isBefore(start) && now.isBefore(end);
    }
}
```

```java
// 운영: 호출할 때마다 현재 시각을 읽는다.
Promotion promotion = new Promotion(Clock.systemUTC());

// 테스트 설정 예시: 시작 시각에 고정된 시계를 사용한다.
Instant start = Instant.parse("2026-09-14T10:00:00Z");
Instant end = Instant.parse("2026-09-14T11:00:00Z");
Clock clock = Clock.fixed(start, ZoneOffset.UTC);
Promotion testPromotion = new Promotion(clock);
boolean active = testPromotion.isActive(start, end); // 예상: true
```

`Z`는 UTC 기준 시각을 뜻한다. `Clock.fixed`가 제공하는 시각은 실제 시간이 흘러도 바뀌지 않는다. 생성자로 객체를 전달하는 순수 Java 코드만으로 의존성 주입이 성립하며 Spring 빈 등록은 필요하지 않다.

## 현재 시각이라는 값만 전달해도 된다

위의 시계 주입 방식 대신, 호출자가 시각을 정해서 전달하는 방법도 있다.

```java
boolean isActive(Instant start, Instant end, Instant now) {
    return !now.isBefore(start) && now.isBefore(end);
}
```

두 예제는 대안 관계이며 함께 구현해야 하는 구조가 아니다.

| 선택 | 현재 시각을 읽는 책임 | 적합한 상황 |
| --- | --- | --- |
| `Instant` 전달 | 호출자 | 단순한 기간 판단, 여러 판단에 동일한 기준 시각 사용 |
| `Clock` 주입 | 전달받은 시계를 사용하는 객체 | 같은 객체가 여러 호출에서 각 호출 시점의 시각을 읽어야 함 |

예를 들어 기획전 100개를 한 번에 판정한다면 호출자가 `now`를 한 번 구해 모두에게 전달할 수 있다. 판정 도중 시간이 흘러도 같은 기준으로 판단한다. 이 경우에는 시계 객체를 도입하지 않아도 충분하다. 반대로 `Instant`를 생성자에서 한 번 저장하면 이후에도 그 시각을 사용하므로, 계속 갱신되는 현재 시각이 필요한 객체에서는 주의해야 한다.

## 경계 조건과 남은 실습

시작이 10시, 종료가 11시일 때의 예상 결과는 다음과 같다. 아직 실행 결과는 확인하지 않았다.

| 기준 시각 | 예상 노출 여부 | 이유 |
| --- | --- | --- |
| 09:59:59 | false | 시작 전 |
| 10:00:00 | true | 시작 포함 |
| 10:59:59 | true | 진행 중 |
| 11:00:00 | false | 종료 제외 |

설명용 코드는 시간의 출처에 집중하여 null 검사와 기간 검증을 생략했다. 실제 적용에서는 null인 입력과 시작이 종료보다 늦거나 같은 기간을 허용할지 정해야 한다. 이 비교식 자체는 시작과 종료가 같으면 항상 false를 반환한다.

후속 실습에서는 고정된 시계와 직접 전달한 시각으로 같은 경계 결과가 나오는지 확인한다. 원칙은 필요한 자원을 무조건 객체로 포장하는 것이 아니라 내부에서 고정한 선택을 외부에서 제어할 수 있게 만드는 것이다.
