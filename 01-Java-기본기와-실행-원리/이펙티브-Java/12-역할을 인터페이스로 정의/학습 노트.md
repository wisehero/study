# 역할을 인터페이스로 정의

학습일: 2026-09-14 · 학습 순서 12 · 아이템 20: 추상 클래스보다는 인터페이스를 우선하라

## 핵심 결론

공통 역할은 인터페이스로 정의하는 것을 우선 검토한다. 밀접한 클래스들이 공통 상태와 구현을 상속으로 공유해야 한다면 추상 클래스를 검토한다. 객체에 상태가 있다는 사실만으로 추상 클래스를 선택하지 않는다.

인터페이스는 호출자가 어떤 일을 요청할 수 있는지 정의하는 타입이다. 추상 클래스는 직접 인스턴스를 만들 수 없고, 하위 클래스에 공통 필드와 구현을 제공할 수 있는 클래스다. 이 노트의 재고·가격 코드는 개념 설명용이며, 이후 구현한 할인 정책 코드와 테스트 결과는 [실습 기록](실습%20기록.md)에 정리했다.

## 의존성 주입과 인터페이스의 관계

앞 항목의 의존성 주입은 필요한 자원을 외부에서 받는 방법이다. 인터페이스는 그 자원을 어떤 역할의 타입으로 받을지 정하는 방법이다. 구체 클래스를 전달받아도 의존성 주입이며, 두 개념은 동일하지 않다.

주문 서비스가 DB 재고 조회를 담당하는 `DbStockRepository`를 생성자로 받으면 의존성 주입은 적용된다. 하지만 받을 수 있는 타입은 그 구체 클래스에 묶여 있다. 재고 조회라는 역할을 별도로 정의하면 호출자는 조회 구현을 몰라도 된다.

```java
interface StockRepository {
    int findStock(String productCode);
}

class OrderService {
    private final StockRepository stocks;

    OrderService(StockRepository stocks) {
        this.stocks = stocks;
    }

    boolean canOrder(String productCode, int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("주문 수량은 양수여야 합니다.");
        }
        return stocks.findStock(productCode) >= quantity;
    }
}
```

운영에서는 이 인터페이스를 구현한 DB 조회 객체를 전달한다. 테스트에서는 다음처럼 고정된 재고를 반환하는 객체를 전달할 수 있다.

```java
class FixedStockRepository implements StockRepository {
    @Override
    public int findStock(String productCode) {
        return 10;
    }
}
```

이 객체를 전달한 `OrderService`에 수량 10을 요청하면 true, 11을 요청하면 false, 0을 요청하면 예외가 예상된다. 여기의 테스트용 구현은 모든 상품 코드에 10을 반환하므로 실제 상품 조회나 상품 부재를 재현하지 않는다.

메서드 모양만 같다고 교체 가능한 것은 아니다. 상품이 없을 때 0을 반환할지 예외를 던질지, 조회 실패를 어떻게 전달할지 같은 동작의 계약도 정해야 한다. 조회 실패를 정상 재고 0으로 숨기면 호출자는 품절과 장애를 구분하지 못한다. 또한 이 예제는 재고 조회 결과를 비교할 뿐이며, 동시 주문의 재고 차감까지 보장하지 않는다.

## 모든 클래스에 인터페이스가 필요한 것은 아니다

인터페이스를 추가하면 읽을 때 선언과 구현을 오가고, 계약을 변경할 때 구현들도 관리해야 한다. 단순한 계산처럼 구체 클래스로 충분한 경우에는 그 부담이 이점보다 클 수 있다.

다만 구현체의 개수만으로 결정하지 않는다. DB나 외부 결제처럼 업무 로직과 분리할 경계가 명확하면 운영 구현이 하나여도 유용할 수 있다. 실제 교체 필요, 테스트에서 제어할 부분, 호출자에게 제공할 역할을 근거로 선택한다. 막연히 구현이 늘어날 수 있다는 이유만으로 일괄 도입하지 않는다.

## 구현을 교체한 뒤 이전 구현을 삭제해도 된다

A 인터페이스를 구현한 B를 C로 완전히 대체했다면 사용하지 않는 B는 삭제할 수 있다. 인터페이스의 이점이 성립하려고 여러 구현을 계속 보관할 필요는 없다. 호출자가 A의 계약에만 의존한다면 구현 교체가 호출자의 업무 코드로 퍼지는 것을 줄일 수 있다.

다만 구체 클래스의 공개 메서드를 유지하며 내부만 바꾸는 방법도 있다. 호출부가 적고 그 방식으로 충분하다면 교체를 위해 인터페이스를 추가할 필요는 없다. 구현 개수보다 사용하는 코드와 구현의 변화를 분리할 필요가 있는지가 기준이다.

## 인스턴스 상태와 공통 동작의 차이

추상 클래스는 객체마다 다른 값인 인스턴스 상태를 필드로 보관하고 생성자로 초기화할 수 있다.

```java
abstract class Product {
    private final int price;

    protected Product(int price) {
        this.price = price;
    }

    public int price() {
        return price;
    }
}
```

인터페이스는 인스턴스 필드와 생성자를 가질 수 없다. 인터페이스에 선언한 필드는 모두 `public static final`이며, 객체별 상태를 저장하는 필드가 아니다. 다만 final인 참조가 가리키는 객체까지 불변인 것은 아니다.

인터페이스도 `default` 메서드로 공통 동작을 제공할 수 있다. 필요한 상태는 구현 객체가 제공하게 한다.

```java
interface Priced {
    int price();

    default boolean isFree() {
        return price() == 0;
    }
}
```

`Priced`는 가격을 저장하지 않고 구현 객체의 `price()`를 호출한다. 이를 구현한 클래스는 자기 `price` 필드를 가질 수 있다. 따라서 상태가 필요한지보다 공통 부모가 그 상태를 보관하고 관리해야 하는지가 판단 기준이다. 위 가격 예제는 구조 설명을 위해 값 검증을 생략했다.

## 상속 제약과 선택 기준

Java 클래스는 클래스 하나만 상속할 수 있지만 인터페이스는 여러 개 구현할 수 있다. 인터페이스를 사용하면 이미 다른 클래스를 상속한 객체에도 가격 제공 같은 역할을 추가할 수 있다. 이것이 아이템 20에서 인터페이스를 우선 검토하는 중요한 이유다.

| 기준 | 인터페이스 | 추상 클래스 |
| --- | --- | --- |
| 중심 목적 | 호출자에게 제공할 역할과 계약 정의 | 관련 하위 클래스의 공통 상태와 구현 공유 |
| 인스턴스 상태 | 구현 클래스가 보관 | 공통 부모에 보관 가능 |
| 공통 동작 | default 메서드 등으로 제공 가능 | 일반 메서드 등으로 제공 가능 |
| 타입 확장 | 클래스가 여러 인터페이스 구현 가능 | 클래스는 하나의 클래스만 상속 가능 |

둘을 함께 사용할 수도 있다. 인터페이스로 역할을 공개하고, 필요한 구현들만 선택적으로 공통 추상 클래스를 상속하게 할 수 있다. 이는 후속으로 살펴볼 설계이며 이번 대화에서 구현하지 않았다.
