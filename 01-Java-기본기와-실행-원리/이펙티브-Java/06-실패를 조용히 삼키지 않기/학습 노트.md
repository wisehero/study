# 실패를 조용히 삼키지 않기

학습일: 2026-09-11 · 학습 순서 06 · 아이템 77

## 핵심 결론

예외를 잡은 뒤에는 복구하거나 실패를 호출자에게 전달한다. 로그만 남기는 것으로 실패 처리가 끝나지는 않는다. 코드 리뷰에서는 “이 처리가 끝난 뒤 호출자는 무엇을 사실이라고 믿게 되는가?”를 확인한다.

이 노트는 대화에서 다룬 개념과 설명용 코드를 정리한다. 이후 구현한 짧은 비교 코드와 검증 결과는 [실습 기록](실습%20기록.md)에 정리했다.

## 빈 catch와 로그만 남기는 catch의 문제

가격 변경 중 저장소 오류가 발생했다고 가정한다.

```java
try {
    repository.updatePrice(productId, price);
} catch (Exception e) {
    // 아무 처리도 하지 않음
}
```

메서드가 정상 종료되므로 호출자는 실패를 전달받지 못한다. 실제 가격은 바뀌지 않았는데 화면에는 변경 완료가 표시될 수 있다.

```java
catch (Exception e) {
    log.error("가격 변경 실패", e);
}
```

로그를 남겨도 호출자 관점에서는 같다. 로그는 운영자가 확인할 기록이며 호출자에게 실패를 전달하는 수단이 아니다. 위 코드는 문제를 설명하기 위한 조각이며, 실제로 잡을 예외는 처리 가능한 종류로 좁히는 편이 좋다.

## 복구할 수 없다면 전달한다

현재 메서드에서 할 수 있는 일이 없다면 불필요하게 catch하지 않는다.

```java
public void changePrice(long productId, int price) {
    repository.updatePrice(productId, price);
}
```

이 예제는 저장소가 비검사 예외를 던지는 경우다. 검사 예외를 던지는 메서드라면 throws 선언 또는 적절한 변환이 필요하다. 호출자는 전달된 실패에 맞는 응답을 결정할 수 있다.

호출 계층에서 이해할 수 있는 의미로 예외를 바꾸어 전달할 때는 원인을 보존한다.

```java
catch (SQLException e) {
    throw new IllegalStateException("가격 변경에 실패했습니다.", e);
}
```

SQLException은 DB 작업의 검사 예외다. 생성자의 마지막 인자 e는 원인 예외이며, 이를 보존해야 구체적인 실패 원인을 추적할 수 있다. IllegalStateException은 여기서 변환 방식을 보여주기 위한 예이며 모든 DB 오류에 일괄 적용하는 규칙은 아니다.

## 복구와 의도적인 무시

복구 가능한 실패라면 재시도나 대체 동작으로 요청의 계약을 충족할 수 있다. 선택 사항인 부가 기능의 실패가 핵심 작업의 성공을 바꾸지 않도록 설계할 수도 있다.

다만 실패를 무시하려면 그 조건과 이유를 코드에 남기고 필요한 로그·지표 등 관측 방법을 정한다. 무조건 매번 로그를 남겨야 한다는 뜻은 아니다. “실패해도 성공으로 처리하기로 설계함”과 “실패를 모르고 지나침”은 구분해야 한다.

## 실무에서 함께 확인할 세 가지

### 로그 중복

저장소·서비스·컨트롤러가 같은 예외의 로그를 각각 남기면 한 번의 실패가 여러 번 기록된다. 보통 오류를 최종 처리하는 경계에서 필요한 작업 문맥과 함께 기록하고 중간 계층은 전달한다. 각 계층에 별도 기록이 필요한 이유가 있다면 구분한다.

### 재시도 전 처리 여부

외부 요청의 시간 초과는 원격 작업이 실패했다는 증거가 아니다. 결제는 완료됐지만 응답만 받지 못했을 수 있다. 무조건 재시도하면 중복 처리가 생길 수 있으므로, 같은 요청을 여러 번 받아도 중복 효과를 막는 요청 식별자나 처리 결과 조회 등을 고려한다. 확실한 실패와 처리 여부를 모르는 상황은 다르다.

### 기본값의 의미

```java
try {
    return repository.findStock(productId);
} catch (Exception e) {
    return 0;
}
```

이 코드는 “재고 조회 실패”를 “재고 없음”으로 바꾼다. 검색 실패를 빈 목록으로 반환하는 것도 같은 문제다. 기본값으로 대체하려면 실제 결과와 대체 결과를 호출자가 구분해야 하는지 먼저 정해야 한다. 이는 앞에서 배운 빈 목록과 null의 의미 구분과 연결된다.

## 실습 연결

검색 실패를 빈 목록으로 숨기는 예제와 원인을 보존해 전달하는 개선 예제를 구현했다. 정상 빈 결과, 정상 상품 결과, 실패를 테스트로 확인했다. 구현과 결과는 실습 기록을 참고한다.
