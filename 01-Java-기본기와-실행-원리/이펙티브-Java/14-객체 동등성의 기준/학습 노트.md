# 객체 동등성의 기준

학습일: 2026-09-14 · 학습 순서 14 · 아이템 10: equals는 일반 규약을 지켜 재정의하라

## 핵심 결론

객체가 같다는 의미를 먼저 정한다. 동일한 인스턴스인지 확인하는 것과 서로 다른 인스턴스가 같은 값을 나타내는지 확인하는 것은 다르다. 값으로 동등성을 정의하려면 `equals()`를 재정의하고 다섯 가지 일반 규약을 지켜야 한다. `hashCode()`도 함께 재정의해야 한다.

이 노트는 대화의 설명용 코드와 판단 기준을 정리한다. 이후 Java Lab의 [ProductCode](../../../java-lab/src/main/java/dev/study/javalab/collections/ProductCode.java)를 record에서 일반 클래스로 전환하고 테스트했다. 아래 코드는 개념 설명용이며, 실제 코드와 실행 결과는 [실습 기록](실습%20기록.md)에 정리했다.

## 동일성과 동등성

참조 타입에서 `==`는 두 참조가 동일한 객체를 가리키는지 비교한다. `equals()`를 재정의하지 않은 일반 클래스는 최상위 클래스 `Object`의 구현을 사용하므로 역시 객체의 동일성을 기준으로 판단한다.

```java
class ProductCode {
    private final String value;

    ProductCode(String value) {
        this.value = value;
    }
}
```

```java
var first = new ProductCode("P001");
var second = new ProductCode("P001");

first == second;       // 예상: false
first.equals(second); // 예상: false
```

두 객체는 각각 생성됐으므로 동일한 객체가 아니다. 필드 내용이 같다고 자동으로 동등해지지도 않는다. 상품 코드처럼 값을 나타내는 객체에서는 내부 문자열이 같으면 같은 코드로 판단하는 것이 적합할 수 있다. 반면 각 인스턴스 자체의 구별이 중요한 객체는 기본 동작으로 충분할 수 있다. 모든 클래스의 모든 필드를 일괄 비교하는 것이 목표는 아니다.

## 상품 코드 값으로 비교하는 구현

다음은 위 클래스를 대체하는 구현이다. 같은 파일에 두 클래스를 함께 선언하는 예제가 아니다.

```java
public final class ProductCode {
    private final String value;

    public ProductCode(String value) {
        this.value = java.util.Objects.requireNonNull(value);
    }

    @Override
    public boolean equals(Object other) {
        if (this == other) {
            return true;
        }
        if (!(other instanceof ProductCode that)) {
            return false;
        }
        return value.equals(that.value);
    }

    @Override
    public int hashCode() {
        return value.hashCode();
    }
}
```

먼저 같은 객체이면 true를 반환한다. 다른 타입이나 null이면 false를 반환하고, 같은 타입이면 문자열의 내용을 비교한다. `instanceof ProductCode that`은 타입을 확인하면서 해당 객체를 `that`이라는 변수로 사용할 수 있게 하는 문법이다. null은 이 타입 검사에서 false가 된다.

| 비교 | 예상 결과 | 기준 |
| --- | --- | --- |
| 별도로 만든 두 `ProductCode("P001")`의 `==` | false | 서로 다른 객체다. |
| 같은 두 객체의 `equals` | true | 상품 코드 문자열이 같다. |
| `P001`과 `P002` 객체의 `equals` | false | 상품 코드 문자열이 다르다. |
| `ProductCode("P001").equals(null)` | false | null과 동등하지 않다. |
| `ProductCode("P001").equals("P001")` | false | 문자열 자체와는 타입이 다르다. |

클래스의 final은 상속을 막아 자식이 동등성 기준을 바꾸는 문제를 피하게 한다. 필드의 final과 불변 타입인 String은 생성 후 비교 기준을 유지한다. null을 거절했으므로 문자열 비교와 해시 계산도 null 없이 수행할 수 있다. 예제에서는 빈 문자열·공백 검증을 생략했으며, 실제 실습 코드에서 유지한 입력 검증과는 차이가 있다.

## equals의 다섯 가지 일반 규약

아래의 a·b·c는 null이 아닌 객체를 뜻한다.

| 규약 | 의미 |
| --- | --- |
| 반사성 | `a.equals(a)`는 true다. |
| 대칭성 | `a.equals(b)`와 `b.equals(a)`의 결과가 같다. |
| 추이성 | a와 b가 같고 b와 c가 같으면 a와 c도 같다. |
| 일관성 | 비교에 사용하는 정보가 바뀌지 않으면 반복 비교 결과가 같다. |
| null 비교 | `a.equals(null)`은 false다. |

일관성은 모든 객체가 불변이어야 한다는 뜻은 아니다. 비교에 쓰는 정보가 그대로인데 외부 상황에 따라 결과가 달라지면 안 된다는 조건이다. 가변 객체를 해시 컬렉션에서 사용할 때의 별도 문제는 다음 학습에서 다룬다.

## 다른 타입까지 비교하면 대칭성을 깨뜨릴 수 있다

상품 코드 객체가 같은 내용의 String과도 같다고 판단하도록 구현했다고 가정한다.

```java
code.equals("P001"); // true로 구현했다고 가정
"P001".equals(code); // false: String은 ProductCode와 동등하다고 보지 않는다.
```

비교 방향에 따라 결과가 달라져 대칭성을 위반한다. 편의상 비교 대상 타입을 넓히기보다 동등성의 범위와 상대 타입의 규칙까지 확인해야 한다. 위의 final 클래스는 같은 ProductCode 타입끼리만 비교하여 이 문제를 피한다.

## 다음 학습과 남은 실습

`equals()`로 동등한 객체는 반드시 같은 해시값을 반환해야 한다. 따라서 위 구현은 문자열을 동등성 기준으로 사용하면서 같은 문자열의 `hashCode()`도 반환한다. 자세한 내용은 [15번 학습 노트](../15-동등성과%20해시의%20일관성/학습%20노트.md)에 정리했다.

기존 record를 일반 클래스로 전환하고, 위 규약과 null·다른 타입 비교를 테스트했다. 직접 비교 구현을 바꾸고 결과를 설명하는 학습 확인은 남아 있다. 영속성 엔티티의 식별자나 상속을 허용한 값 클래스의 동등성 설계는 이번 대화 범위 밖이다.
