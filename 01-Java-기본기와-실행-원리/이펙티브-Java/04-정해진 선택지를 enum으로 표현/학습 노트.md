# 정해진 선택지를 enum으로 표현

학습일: 2026-09-11 · 학습 순서 04 · 아이템 34

## 핵심

고정된 선택지를 enum 타입으로 정의하면 허용되지 않은 문자열이나 다른 종류의 값을 컴파일 시점에 막을 수 있다. 여러 곳에서 정의를 공유하는 것뿐 아니라 메서드 인자의 종류를 제한한다는 점이 중요하다.

```java
void changeStatus(ProductStatus next) { /* 검증 후 변경 */ }
// changeStatus("서울"); // 타입이 달라 컴파일 오류
```

## 상태 전이는 누가 검사하는가

상태만으로 판단하는 전이 규칙은 enum에 둘 수 있다. 상품 도메인 메서드는 그 규칙을 검사하고 실제 상태를 변경한다. 가격·재고 등 다른 상품 정보가 필요한 규칙은 도메인 메서드에서 함께 검증한다. enum도 null은 가능하므로 필수 값 검증은 필요하다.

이번 예제는 READY → ON_SALE → DISCONTINUED만 허용한다. 단, 같은 상태의 재요청은 도메인 메서드에서 변경 없이 성공 처리한다. 재시도에도 같은 결과를 유지하는 동작이며, 알림·이벤트 발행까지 중복 방지하는 구현은 포함하지 않는다. 실패하면 기존 상태를 유지한다.

## 저장과 외부 입력

ordinal()은 선언 순서이므로 저장 코드로 쓰지 않는다. 중간에 상태를 추가하면 기존 숫자의 의미가 달라질 수 있다. 예제에서는 명시적인 code 필드를 두고 fromCode로 변환한다. DB·JSON이 자동으로 이 필드를 사용하는 것은 아니며 실제 연결은 별도 구현해야 한다.

valueOf는 code가 아니라 상수 이름을 대소문자까지 정확히 비교한다. 따라서 ON_SALE의 외부 코드를 on_sale로 정한 이번 예제는 fromCode("on_sale")을 사용한다. null과 모르는 코드는 거절하며 임의의 기본 상태로 바꾸지 않는다. 코드와 화면 문구(판매 중, On sale)는 분리한다.

## 실무에서 확인할 점

- 같은 상태 요청을 실패로 볼지, 변경 없는 성공으로 볼지 정한다. 부수 효과가 있다면 재시도 시 중복 실행도 고려한다.
- 새 상태 추가 시 전이 규칙, 조회 필터, 집계, 이전 클라이언트의 처리와 배포 호환성을 확인한다.
- 운영자가 자유롭게 추가해야 하는 브랜드·카테고리 등은 enum보다 데이터 관리가 적합할 수 있다.
- 숫자나 문자열 상수는 잘못된 값을 허용하기 쉽지만, enum도 외부 입력과 업무 전이 규칙까지 자동 보장하지는 않는다.
