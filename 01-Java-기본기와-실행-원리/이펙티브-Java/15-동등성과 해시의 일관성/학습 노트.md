# 동등성과 해시의 일관성

학습일: 2026-09-14 · 학습 순서 15 · 아이템 11: equals를 재정의하려거든 hashCode도 재정의하라

## 핵심 결론

`equals()`가 true인 두 객체는 같은 `hashCode()`를 반환해야 한다. 반대로 해시값이 같다고 동등한 객체인 것은 아니다. 해시 컬렉션에 저장한 동안에는 동등성과 해시 계산에 사용하는 정보를 바꾸지 않는 것이 중요하다.

이 노트는 대화에서 설명한 동작과 판단 기준을 정리한다. 설명용 ProductCode는 [14번 노트](../14-객체%20동등성의%20기준/학습%20노트.md)의 일반 클래스를 기준으로 한다. 이후 구현한 정상·문제 재현 테스트와 실행 결과는 [실습 기록](실습%20기록.md)에 정리했다.

## 해시 컬렉션은 먼저 비교 후보를 좁힌다

`hashCode()`는 객체의 해시값을 int로 반환한다. `HashSet`은 값의 중복을 관리하는 집합이고, `HashMap`은 키에 값을 연결하는 자료구조다. 이들은 해시값으로 저장·검색 위치와 비교 후보를 좁힌 뒤 같은지 확인한다.

```text
hashCode로 저장 위치와 비교 후보를 좁힘
  → 후보와 equals로 동등성 확인
    → 같으면 같은 원소 또는 키로 처리
```

이는 이해를 위한 개념 흐름이다. 실제 구현은 해시값을 가공하거나 같은 참조인지 먼저 확인할 수 있다. 해시값이 같으면 항상 equals를 호출한다거나, 해시값이 곧 배열 인덱스라는 뜻은 아니다.

## equals만 재정의하면 생기는 문제

상품 코드 문자열로 `equals()`를 구현했지만 `hashCode()`는 생략했다고 가정한다.

```java
var first = new ProductCode("P001");
var second = new ProductCode("P001");
first.equals(second); // 예상: true

var codes = new HashSet<ProductCode>();
codes.add(first);
codes.add(second);
codes.size(); // 1을 기대하지만 2가 될 수 있다.
```

기본 해시 계산은 우리가 정한 상품 코드의 동등성을 반영하지 않는다. 두 객체의 해시값이 다르면 해시 컬렉션에서 같은 원소로 처리되지 않을 수 있다. 서로 다른 객체의 기본 해시값이 반드시 다르다는 보장도 없으므로 위 결과를 무조건 2라고 단정하지 않는다.

문자열을 동등성 기준으로 삼았다면 해시 계산도 그 문자열을 사용한다.

```java
@Override
public int hashCode() {
    return value.hashCode();
}
```

이제 같은 상품 코드 문자열을 가진 두 객체는 해시값과 equals 결과가 일치하여 집합에 하나만 남는다. null은 생성자에서 거절한다는 전제다.

## 정확성과 분산 성능은 구분한다

서로 다른 값이 같은 해시값을 갖는 현상을 해시 충돌이라고 한다. 충돌은 허용되며 equals로 동등성을 구분할 수 있다.

```text
equals가 true → hashCode가 같아야 한다.
hashCode가 같음 → equals가 true일 필요는 없다.
```

다음 구현은 모든 객체에 같은 해시값을 반환한다.

```java
@Override
public int hashCode() {
    return 1;
}
```

이 구현은 같은 값의 객체에도 같은 해시값을 반환하므로 규약 위반은 아니다. equals가 올바르면 중복 판정도 정확하다. 문제는 서로 다른 값이 같은 위치에 몰려 후보를 좁히는 효과를 잃고 저장·조회 비용이 커질 수 있다는 점이다. 이번 학습에서는 성능을 측정하지 않았으며 구체적인 시간 복잡도를 단정하지 않는다.

좋은 구현은 동등한 객체의 해시값을 일치시키는 정확성과, 다른 값을 가능한 한 분산시키는 성능을 함께 고려한다. 충돌을 완전히 없애거나 해시값을 고유 식별자로 만드는 것이 목표는 아니다.

비교에 쓰는 정보가 바뀌지 않는 한 한 번의 프로그램 실행 동안 같은 객체의 해시값도 일관돼야 한다. 프로그램을 다시 실행했을 때까지 같은 해시값을 유지해야 하는 일반 규약은 없다.

## 저장한 뒤 비교 기준을 바꾸면 조회가 깨질 수 있다

이번에는 ProductCode의 value를 수정할 수 있게 바꿨다고 가정한다. 앞의 final 필드를 가진 클래스에는 `changeValue`가 없으며 다음 코드를 그대로 실행할 수 있는 것은 아니다.

```java
var code = new ProductCode("P001");
var codes = new HashSet<ProductCode>();

codes.add(code);
code.changeValue("P002"); // 변경 가능한 별도 구현이라고 가정

codes.contains(code); // 같은 객체여도 false가 될 수 있다.
```

저장할 때는 P001의 해시값을 사용했지만 조회할 때는 P002의 해시값을 사용한다. 컬렉션은 필드 변경을 감지하여 자동으로 재배치하지 않는다. 객체가 남아 있어도 현재 해시값으로 찾지 못할 수 있으며, 저장된 원소를 바꿔도 안전하다고 가정해서는 안 된다.

안정적으로 사용하려면 HashSet의 원소나 HashMap의 키로 저장된 동안 equals와 hashCode의 기준이 유지되게 한다. 객체의 모든 필드가 반드시 불변이어야 하는 것은 아니며, 동등성과 해시 계산에 참여하지 않는 상태는 별개다. HashMap에서는 값(value)이 아니라 키(key)에 관한 주의사항이다.

앞의 예제는 `private final String value`로 비교 기준을 유지한다. final 필드는 재할당을 막고 String 자체도 불변이다. 가변 객체를 가리키는 final 참조라면 내부 상태 변경까지 막지 못하므로 같은 보장으로 볼 수 없다.

## 남은 실습

동등한 서로 다른 상품 코드의 HashSet 중복 제거와 HashMap 저장·조회를 검증했다. 해시 계약 위반, 상수 해시값의 정확성, 가변 키의 조회·삭제 실패도 테스트 전용 예제로 확인했다. 직접 구현을 바꾸어 결과를 설명하는 학습 확인은 남아 있으며, 성능 측정은 하지 않았다.
