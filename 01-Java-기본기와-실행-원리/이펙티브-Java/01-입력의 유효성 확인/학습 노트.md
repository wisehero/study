# 입력의 유효성 확인 — 학습 노트

학습일: 2026-09-11 · 학습 순서: 01/30 · 관련 항목: Effective Java 3판 아이템 49

## 핵심 결론

호출 경로와 관계없이 업무 규칙을 보장하고, 모든 입력 검증을 상태 변경 전에 끝낸다. 잘못된 입력을 테스트할 때는 예외 발생뿐 아니라 기존 상태가 유지되는지도 확인한다.

이 노트는 대화에서 학습한 내용을 정리한다. 아래 코드는 설명용이며, 실습 프로젝트에 구현하거나 테스트를 실행한 결과는 아니다.

## 검증이 필요한 이유와 책임

컨트롤러는 HTTP 요청을 받아 처리하는 진입점이다. 특정 API의 컨트롤러에서 입력을 검사하더라도, 다른 도메인과의 협력이나 배치 등 다른 호출 경로에서는 그 검사를 거치지 않을 수 있다.

따라서 가격을 관리하는 도메인 객체는 “가격은 음수일 수 없다”처럼 항상 지켜야 하는 업무 규칙을 스스로 보장해야 한다.

- 컨트롤러에서는 요청의 필수 값과 형식 등을 검사한다.
- 도메인 객체에서는 호출 경로와 관계없이 유효한 업무 상태를 보장한다. 필수 값 여부도 업무 규칙이라면 이곳에서 보장해야 한다.

두 위치에서 같은 조건을 검사할 수 있다. 요청 단계의 검사는 잘못된 요청을 일찍 거절하고, 도메인 객체의 검사는 다른 경로에서도 규칙을 유지하는 역할을 한다.

## 검증을 상태 변경보다 먼저 수행한다

가격이 0 이상이어야 한다고 가정한다. 아래 구현은 잘못된 예다.

```java
public void changePrice(int price) {
    this.price = price;

    if (price < 0) {
        throw new IllegalArgumentException("가격은 0 이상이어야 합니다.");
    }
}
```

기존 가격이 1000일 때 -1을 전달하면 예외는 발생하지만 가격은 이미 -1로 바뀐다. 호출자가 예외를 잡아도 실행된 대입은 자동으로 취소되지 않는다.

다음처럼 검사 후 대입해야 한다. `IllegalArgumentException`은 메서드가 허용하지 않는 인자가 전달되었음을 나타내는 예외다.

```java
public void changePrice(int price) {
    if (price < 0) {
        throw new IllegalArgumentException("가격은 0 이상이어야 합니다.");
    }

    this.price = price;
}
```

이 규칙에서는 0원도 허용한다. -1은 거절하고, 실패 시 기존 가격을 유지한다. 0원을 허용할지는 실제 업무 규칙에 따라 정해야 한다.

## 관련된 값은 관계까지 모두 검증한다

상품 노출 기간의 규칙을 “시작일과 종료일은 필수이며, 종료일은 시작일보다 뒤여야 한다”로 정한다. 시작일만 검사하고 저장한 뒤 종료일을 검사하면, 종료일 검사 실패 시 시작일만 변경된 상태가 남을 수 있다.

```java
public void changeDisplayPeriod(
        LocalDateTime start, LocalDateTime end) {

    Objects.requireNonNull(start, "노출 시작일은 필수입니다.");
    Objects.requireNonNull(end, "노출 종료일은 필수입니다.");

    if (!end.isAfter(start)) {
        throw new IllegalArgumentException(
                "노출 종료일은 시작일보다 뒤여야 합니다.");
    }

    this.start = start;
    this.end = end;
}
```

`LocalDateTime`은 시간대 정보 없는 날짜와 시간을 나타내는 타입이다. `Objects.requireNonNull`은 값이 `null`이면 `NullPointerException`을 발생시키는 표준 검사 메서드다. 위 예제에는 각각 `java.time.LocalDateTime`, `java.util.Objects`의 import와 해당 필드를 가진 클래스가 필요하다.

두 값의 필수 여부와 시간의 선후 관계를 모두 검사한 다음 필드에 대입한다. 이 규칙에서는 시작일과 종료일이 같은 경우도 거절한다.

여기서 함께 반영한다는 것은 검증을 모두 통과한 후 대입한다는 뜻이다. 두 필드의 대입이 다른 스레드에도 하나의 연산처럼 보인다는 보장은 아니다. 동시 접근은 별도 설계가 필요하다.

## 테스트에서 확인할 내용

예외 발생만 검사하면 일부 필드가 이미 바뀐 버그를 놓칠 수 있다. 실패한 작업이 객체를 기존 상태로 유지하는 성질을 실패 원자성이라고 한다. 우리 학습 순서 25번에서 더 다룰 개념이다.

예를 들어 기존 기간이 9월 10일 → 9월 20일일 때, 9월 15일 → 9월 14일로 변경을 요청한다면 다음 두 가지를 확인한다.

1. `IllegalArgumentException`이 발생한다.
2. 시작일과 종료일 모두 기존 값인 9월 10일 → 9월 20일을 유지한다.

실습에서 확인할 경계 사례는 다음과 같다. 아래는 예상 결과이며 실행 결과가 아니다.

| 대상 | 입력 | 예상 결과 |
| --- | --- | --- |
| 가격 | -1 | 예외 발생, 기존 가격 유지 |
| 가격 | 0, 1 | 각각 정상 변경 |
| 노출 기간 | 시작일 또는 종료일이 null | 예외 발생, 기존 기간 유지 |
| 노출 기간 | 종료일이 시작일보다 이전 | 예외 발생, 기존 기간 유지 |
| 노출 기간 | 시작일과 종료일이 같음 | 예외 발생, 기존 기간 유지 |
| 노출 기간 | 종료일이 시작일보다 이후 | 두 값을 정상 변경 |
