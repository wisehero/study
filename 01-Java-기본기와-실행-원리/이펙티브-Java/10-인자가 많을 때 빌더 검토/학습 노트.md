# 인자가 많을 때 빌더 검토

학습일: 2026-09-11 · 학습 순서 10 · 아이템 2

## 핵심 결론

빌더는 생성에 필요한 값을 모으는 준비용 객체다. 값을 단계적으로 설정한 뒤 최종 검증을 거쳐 완성된 객체를 만든다. 선택 값이 많거나 같은 타입의 인자가 반복될 때 호출 의도를 읽기 쉽게 해준다.

이 노트는 대화에서 학습한 개념과 설명용 코드다. 이후 구현한 짧은 코드와 검증 결과는 [실습 기록](실습%20기록.md)에 정리했다.

## 인자가 많으면 의미를 읽기 어렵다

```java
new Product("크림", 10000, 100, true, false, null);
```

숫자와 boolean 값이 각각 무엇을 뜻하는지 생성자 선언을 찾아봐야 한다. 빌더(builder)는 설정할 값에 이름을 드러낸다.

```java
Product product = new Product.Builder("크림", 10000)
        .stock(100)
        .freeShipping(true)
        .build();
```

이 설계에서는 상품명과 가격을 필수 인자로 받고 재고와 무료배송을 선택적으로 설정한다. 정적 팩터리가 “어떤 객체를 만드는가”에 이름을 붙인다면, 빌더는 “어떤 값을 설정하는가”를 드러낸다. 둘은 함께 사용할 수도 있다.

## setter와 빌더의 차이

setter는 이미 만들어진 객체의 값을 바꾸는 메서드다. 다음처럼 여러 호출을 마쳐야 유효해지는 설계라면 중간에 불완전한 상품이 존재할 수 있다.

```java
Product product = new Product();
product.setName("크림");
// 이 시점의 상품에는 가격을 아직 설정하지 않았다.
product.setPrice(10000);
```

반면 빌더는 준비용 객체에 값을 모은 뒤 실제 상품을 생성한다.

```java
Product.Builder builder = new Product.Builder("크림", 10000);
builder.stock(100);                 // 생성에 필요한 값을 준비한다.
Product product = builder.build(); // 검증 후 완성된 상품을 반환한다.
```

- Builder는 생성 설정을 모으고 변경하는 역할이다.
- Product는 최종 검증을 통과한 결과이며 setter 없이 설계할 수 있다.

모든 setter가 잘못이라는 뜻은 아니다. 이미 유효한 객체에서 업무 규칙을 검사하며 변경하는 메서드는 별개의 역할이다. 문제는 여러 설정 호출 사이에 불완전한 상태가 노출되는 설계다.

## 유효성과 불변성은 별도로 보장한다

빌더 문법 자체가 검증이나 불변성을 보장하지 않는다. 각 입력은 설정 시점에 검사할 수 있지만, 기간의 선후 관계처럼 여러 값의 관계는 최종 구성 전체를 기준으로 확인해야 한다. build 또는 그 안에서 호출하는 생성자가 검증에 실패하면 완성된 객체를 반환하지 않도록 한다.

필수 인자를 빌더 생성자로 받더라도 null·빈 문자열·음수 등을 자동으로 막지는 못한다. 완성된 객체가 변경되지 않게 하려면 필드와 메서드 접근 범위도 설계해야 한다. 가변 목록을 빌더와 결과 객체가 공유하면 외부 변경이 영향을 줄 수 있으므로 필요한 복사도 고려한다. 이는 앞에서 배운 입력 검증과 내부 상태 보호의 연결이다.

## 기본값도 계약이다

stock을 생략했을 때 재고가 0인지, 미입력 오류인지 정해야 한다. 준비용 객체의 int 필드가 기본적으로 0이라는 이유만으로 업무 의미가 결정되지는 않는다.

누락을 구분해야 한다면 빌더에서 별도 표시나 박싱 타입을 사용하고 최종 검증에서 필수 여부를 확인할 수 있다. 0을 기본값으로 허용한다면 호출자에게 그 의미를 명확히 알려야 한다.

## 선택 기준과 비용

- 필수 값 몇 개뿐이면 생성자나 정적 팩터리만으로 충분할 수 있다.
- 선택 값이 많거나 같은 타입의 인자가 반복되면 빌더의 가독성 이점이 커진다.
- 빌더 클래스와 설정 코드가 늘고 준비용 객체도 필요하다. 실제 성능 영향은 측정 없이 단정하지 않는다.
- 필드 수만으로 일괄 적용하지 말고 호출부의 이해도와 유효한 객체를 만드는 과정이 단순해지는지 판단한다.

## 실습 연결

상품 예제로 기본값, 최종 입력 검증, 빌더 변경과 결과 객체의 분리를 확인했다. 코드와 실행 결과는 실습 기록을 참고한다. 기획전과 여러 필드 간 관계 검증은 후속 범위다.
