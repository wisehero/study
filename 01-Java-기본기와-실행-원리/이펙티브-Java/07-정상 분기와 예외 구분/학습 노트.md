# 정상 분기와 예외 구분

학습일: 2026-09-11 · 학습 순서 07 · 아이템 69

## 핵심 결론

정상 흐름은 조건문·반복문·반환값으로 표현하고, 계약을 수행하지 못하는 실패는 정확한 의미로 전달한다. 같은 상황이라도 메서드의 목적에 따라 정상 결과일 수도, 실패일 수도 있다. 발생 빈도만으로 예외 사용 여부를 정하지 않는다.

이 노트는 대화에서 다룬 개념과 설명용 코드다. 실습 구현과 실행 검증은 아직 하지 않았다.

## 반복 종료에 예외를 사용하면 내부 버그도 숨길 수 있다

```java
try {
    int i = 0;
    while (true) {
        show(products.get(i++));
    }
} catch (IndexOutOfBoundsException e) {
    // 목록 끝에 도달했다고 가정한다.
}
```

IndexOutOfBoundsException은 유효한 인덱스 범위를 벗어났을 때 발생하는 예외다. 위 코드는 목록 끝을 정상 종료 신호로 삼지만, show 내부에서 같은 예외가 발생해도 잡는다. 그러면 처리를 중간에 멈추고도 정상적으로 완료한 것처럼 보인다.

```java
for (Product product : products) {
    show(product);
}
```

명시적인 반복문을 쓰면 목록 끝은 반복문이 처리하고, show의 실패는 호출자에게 전달된다. 예외로 정상 흐름을 표현하지 않아야 실제 오류가 드러난다.

## 같은 부재라도 계약에 따라 의미가 다르다

“있으면 가져오기” 조회라면 결과 부재를 Optional로 표현할 수 있다. Optional은 단일 결과가 있을 수도 없을 수도 있음을 나타내는 타입이다. 반면 “반드시 존재하는 상품의 가격을 변경하라”는 요청에서 상품 부재는 작업을 수행하지 못하는 이유다.

회원가입에서도 확인과 실행을 구분한다.

```java
boolean existsByUsername(String username); // 이미 사용 중인가?
Member register(String username);          // 가입해라.
```

- existsByUsername의 true는 중복 여부를 정상적으로 확인한 결과다.
- register에서 중복은 가입을 완료하지 못하는 이유이므로 DuplicateUsernameException 같은 예외로 전달할 수 있다.

가입 실패를 반드시 예외로만 표현해야 하는 것은 아니다. 실패 결과 타입으로 표현하는 설계도 가능하다. 중요한 것은 호출자가 성공·정상적인 부정 결과·실패를 구분할 수 있는 계약이다.

## 중복 확인은 가입 성공을 보장하지 않는다

```java
if (!repository.existsByUsername(username)) {
    repository.save(new Member(username));
}
```

확인과 저장 사이에 다른 요청이 실행될 수 있다.

1. 요청 A가 중복 없음을 확인한다.
2. 요청 B도 중복 없음을 확인한다.
3. 요청 A가 저장한다.
4. 요청 B가 같은 아이디 저장을 시도한다.

사전 확인은 빠른 안내에 쓸 수 있지만 최종 중복 방지는 저장 시점에도 보장해야 한다. 예를 들어 DB의 고유 제약 조건은 지정한 값의 중복 저장을 막는다. 가입 메서드는 저장 시 발생하는 충돌도 정확한 가입 실패로 전달해야 한다. 실제 트랜잭션·동시 요청 동작은 이번 대화에서 실행 검증하지 않았다.

## 정상적인 부정 결과와 확인 실패

existsByUsername의 false는 “확인했고, 없다”는 뜻이다. DB 연결 오류를 잡아 false를 반환하면 “확인하지 못했다”를 “없다”로 바꾼다. 정상 분기를 반환값으로 표현하는 메서드에도 실패를 전달할 경로가 필요하다.

가입 중 발생한 모든 예외를 중복 예외로 바꾸어서도 안 된다. 연결 장애나 코드 버그가 중복으로 오해될 수 있다. 다른 필드의 고유 제약 위반도 아이디 중복은 아닐 수 있으므로, 해당 아이디 제약을 위반한 경우에만 의미를 바꾸고 원인을 보존한다.

## 코드 리뷰 기준과 남은 실습

“이 메서드가 답하려는 질문 또는 수행하려는 명령은 무엇인가?”를 먼저 확인한다. 그다음 정상 결과와 계약 실패가 구분되는지, 넓은 catch가 다른 버그까지 숨기지 않는지 점검한다.

실습에서는 예외로 목록 종료를 처리하는 코드와 반복문을 비교하고, 처리 함수 내부에서 같은 종류의 예외가 발생했을 때의 차이를 확인한다. 핵심만 보이는 짧은 코드와 테스트로 구성한다. 실제 DB 중복 제약과 동시 요청은 후속 실습 범위다.
