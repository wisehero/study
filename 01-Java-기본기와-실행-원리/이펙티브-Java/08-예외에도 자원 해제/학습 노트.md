# 예외에도 자원 해제

학습일: 2026-09-11 · 학습 순서 08 · 아이템 9

## 핵심 결론

직접 닫을 책임이 있는 자원에는 try-with-resources를 사용한다. 정상 종료뿐 아니라 예외 발생과 return 시에도 정리를 수행하며, 작업 실패와 정리 실패가 겹치면 작업 예외를 주 예외로 유지한다.

이 노트는 대화에서 다룬 개념과 설명용 코드다. 이후 구현한 짧은 코드와 테스트 결과는 [실습 기록](실습%20기록.md)에 정리했다. 아이템의 핵심인 자원 정리·예외 보존에 자원 소유권과 Spring 사용 맥락을 연결해 정리했다.

## close를 마지막 줄에 두는 것으로는 부족하다

BufferedReader는 텍스트를 읽는 자원이다. 다음 코드에서는 readLine이 실패하면 close까지 도달하지 못한다.

```java
BufferedReader reader = Files.newBufferedReader(path);
String line = reader.readLine();
reader.close();
```

try-with-resources는 자원을 괄호 안에 선언하고 블록을 벗어날 때 close를 호출하는 문법이다.

```java
try (BufferedReader reader = Files.newBufferedReader(path)) {
    return reader.readLine();
}
```

AutoCloseable은 close 메서드를 가진 인터페이스이며 이 문법에 사용할 수 있는 자원의 기준이다. 위 예제에는 java.io.BufferedReader와 java.nio.file.Files 등의 import, path 변수와 IOException 처리 또는 throws 선언이 필요하다.

## 작업과 닫기가 모두 실패하면

| 작업 결과 | close 결과 | 호출자에게 전달되는 결과 |
| --- | --- | --- |
| 성공 | 성공 | 정상 결과 |
| 실패 | 성공 | 작업 예외 |
| 성공 | 실패 | close 예외 |
| 실패 | 실패 | 작업 예외가 주 예외, close 예외는 억제된 예외로 첨부 |

억제된 예외(suppressed exception)는 버려진 예외가 아니다. 주 예외를 덮어쓰지 않고 보존하며 getSuppressed()로 확인할 수 있다. 앞서 예외 변환에서 배운 getCause()의 원인 예외와는 다른 경로다.

반면 다음처럼 단순히 finally에서 닫으면 작업과 close가 모두 실패했을 때 close 예외가 작업 예외를 덮는다.

```java
try {
    return reader.readLine();
} finally {
    reader.close();
}
```

try-with-resources는 닫기를 빠뜨리지 않도록 돕고 최초 작업 실패도 추적하기 쉽게 만든다.

## 여러 자원과 반환 시점

```java
try (InputStream in = Files.newInputStream(source);
     OutputStream out = Files.newOutputStream(target)) {
    in.transferTo(out);
}
```

위 코드는 파일 내용을 복사하는 설명용 예제이며 대상 파일을 생성하거나 기존 내용을 덮어쓸 수 있다. 실제 실습에서는 임시 파일을 사용한다.

- 생성은 in → out, 닫기는 out → in 순서다.
- out 생성에 실패해도 이미 생성된 in은 닫는다. 생성 자체가 실패한 자원의 내부 정리는 그 생성 코드가 책임져야 한다.
- out.close가 실패해도 in.close를 시도한다.
- return 표현식의 값을 구한 후에도 자원을 먼저 닫는다. close가 실패하면 그 값을 반환하지 않고 예외를 전달한다.

자원 해제는 close를 호출한다는 보장이다. close 자체가 실패했을 때 실제 해제까지 완료됐다는 뜻은 아니다. 프로세스 강제 종료와 같은 상황도 일반적인 블록 종료와 구분해야 한다.

## 실무 확장: 누가 닫을 책임을 가지는가

일반적인 Spring Data JPA 저장소 호출에서는 프레임워크가 DB 자원의 수명 관리를 맡으므로 직접 연결을 닫는 코드를 자주 쓰지 않을 수 있다. 반면 직접 연 파일은 자신이 정리할 책임이 있는지 확인해야 한다.

```java
try (Stream<String> lines = Files.lines(path)) {
    return lines.filter(line -> !line.isBlank()).count();
}
```

Files.lines는 열린 파일을 사용하는 스트림이므로 닫아야 한다. list.stream은 보통 외부 자원을 소유하지 않으므로 같은 이유로 닫을 필요가 없다. java.util.stream.Stream 등 필요한 타입의 import와 파일 오류 처리는 별도로 필요하다.

다른 계층이나 프레임워크에서 빌린 자원은 임의로 닫지 않는다. 생성 위치만 보지 말고 자원 소유권과 호출 계약을 확인한다.

close의 실제 의미는 자원마다 다르다. 파일 핸들을 해제하거나 빌린 연결을 풀에 반환할 수 있다. try-with-resources 자체가 작업 취소나 DB 롤백을 자동 보장하는 것은 아니다.
