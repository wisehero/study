# 공부 목표: 시스템 디자인

> 상태: 시작 전 · 작성일: 2026-09-22 · 목표 수준: Java·Spring 미들급 개발자의 독립적인 구현·검증·문제 해결

## 학습 목적

많은 트래픽과 장애를 전제로 시스템의 구성 요소와 데이터 흐름을 설계하고, 선택한 구조의 한계와 비용을 수치로 설명한다. 정답 하나를 외우는 것이 아니라, 주어진 제약에서 대안을 비교하고 근거를 대는 연습이 목적이다.

[10번 주제](../10-아키텍처와-도메인-경계/공부%20목표.md)와 구분한다. 10번은 **한 애플리케이션 안에서 코드를 어디에 둘지**를 다루고, 이 주제는 **애플리케이션 바깥에서 서버·저장소·캐시·큐를 어떻게 배치할지**를 다룬다.

**학습 우선순위:** 다른 주제와 독립적으로 진행할 수 있다. 트랜잭션·정합성은 [3번](../03-트랜잭션과-데이터-정합성/공부%20목표.md), 지표와 병목 해석은 [7번](../07-운영-성능과-보안/공부%20목표.md)에서 다루므로 겹치는 내용이 나오면 해당 문서로 연결한다.

## 범위와 선행 지식

- **이번에 학습할 범위:** 요구사항 정리와 개략 계산, 수평 확장과 무상태 설계, 복제와 분할, 캐시 계층과 무효화, 비동기 큐와 멱등성, 일관성 모델, 장애 대응 패턴, 속도 제한
- **이후에 확장할 범위:** 여러 지역 분산 배치, 합의 알고리즘(Raft, Paxos)의 내부 동작, 스트림 처리와 데이터 웨어하우스, 비용 최적화
- **필요한 선행 지식:** HTTP 요청·응답 흐름, DB 인덱스와 트랜잭션의 기본 개념
- **관련 버전:** 특정 제품·버전에 의존하지 않는다. 제품을 비교해야 하면 그 시점의 공식 문서와 벤치마크로 확인하고 출처를 남긴다.

이 주제는 실행 코드보다 문서와 그림이 산출물의 중심이다. 다만 저장소의 완료 기준을 지키기 위해 설계에서 고른 패턴 하나는 코드로 재현한다.

## 설계 진행 순서

면접과 실무 모두에서 쓰는 4단계다. 연습할 때마다 이 순서를 지키고, 건너뛴 단계가 있으면 이유를 적는다.

1. **요구사항 정리:** 기능 요구와 비기능 요구를 나눈다. 사용자 수, 읽기와 쓰기 비율, 지연시간 목표, 데이터 보관 기간을 질문으로 좁힌다. 가정한 값은 가정이라고 표시한다.
2. **개략 계산:** 초당 요청 수, 저장 용량, 대역폭을 자릿수 수준으로 계산한다. 정확한 값이 아니라 **어느 자원이 먼저 한계에 닿는지**를 찾는 것이 목적이다.
3. **상위 설계:** 클라이언트부터 저장소까지의 구성도를 그리고 각 구성 요소의 책임과 데이터 흐름을 적는다. API 형태와 데이터 모델을 함께 정한다.
4. **상세화와 병목:** 가장 부하가 큰 경로 하나를 골라 깊이 파고, 병목과 장애 시나리오를 지목한 뒤 대안을 비교한다.

## 핵심 개념별 목표

- [ ] **개략 계산**: 사용자 수와 행동 빈도에서 초당 요청 수, 저장 용량, 대역폭을 계산한다. 평균값과 피크값을 구분하고 피크 배수를 가정으로 명시한다.
- [ ] **수평 확장과 무상태(stateless) 설계**: 수직 확장(scale-up)과 수평 확장(scale-out)의 한계를 비교한다. 서버가 상태를 들고 있으면 왜 확장이 막히는지, 세션과 파일을 어디로 옮겨야 하는지 설명한다.
- [ ] **복제(replication)와 분할**: 읽기 복제본으로 해결되는 부하와 해결되지 않는 부하를 구분한다. 샤딩 키 선택이 핫스팟과 범위 조회에 미치는 영향, 재분할의 비용을 설명한다.
- [ ] **캐시 계층과 무효화**: 클라이언트, CDN, 애플리케이션, DB 앞단 중 어디에 둘지 판단한다. 조회 후 채우기(look-aside)와 쓰기 시 갱신(write-through)을 비교하고, TTL 만료가 몰리는 캐시 스탬피드(cache stampede)와 그 완화 방법을 설명한다.
- [ ] **비동기 처리와 메시지 큐**: 요청 처리와 후속 작업을 분리하는 기준을 정한다. 중복 전달과 순서 역전이 기본 전제임을 이해하고, 멱등성(idempotency) 키로 같은 요청의 반복을 안전하게 만든다. 큐가 밀릴 때의 백프레셔와 처리 지연을 다룬다.
- [ ] **일관성 모델**: 강한 일관성과 최종 일관성(eventual consistency)의 차이를 업무 규칙과 연결해 판단한다. 읽기 복제본 지연에서 생기는 문제와 자기가 쓴 것을 읽는 일관성(read-your-writes)을 설명한다. CAP는 구호가 아니라 분할 상황의 선택으로 해석한다.
- [ ] **장애 대응과 성능 저하 설계**: 타임아웃, 재시도와 지수 백오프, 회로 차단기(circuit breaker), 격벽(bulkhead)의 목적을 구분한다. 일부 기능을 끄고 서비스를 유지하는 단계적 성능 저하(graceful degradation)를 설계한다.
- [ ] **속도 제한(rate limiting)과 남용 방지**: 고정 창, 이동 창, 토큰 버킷의 동작과 경계 문제를 비교한다. 제한 단위(사용자, IP, API 키)와 초과 시 응답을 정한다.

## 연습 문제

한 번에 하나씩 고르고, 위의 4단계를 그대로 적용한다. 아래 순서는 필요한 개념이 적은 것부터다.

1. **속도 제한기**: 토큰 버킷과 이동 창을 비교한다. 서버가 여러 대일 때 카운터를 어디에 둘지 정한다.
2. **URL 단축기**: 키 생성 방식(해시, 순번, 미리 생성), 읽기 위주 부하의 캐시 설계, 만료 처리를 다룬다.
3. **알림 발송**: 큐로 분리한 뒤 중복 발송과 실패 재시도를 다룬다. 멱등성 키가 필요한 지점을 찾는다.
4. **뉴스피드**: 쓰기 시 배포(fan-out on write)와 읽기 시 조합(fan-out on read)을 비교한다. 팔로워가 매우 많은 계정을 예외로 다루는 이유를 설명한다.

## 실습 과제

1. 연습 문제 하나를 골라 요구사항, 개략 계산, 구성도, 데이터 모델, API를 한 문서로 작성하고 병목 하나를 지목한다.
2. 같은 문제의 제약을 바꿔 다시 설계한다. 예를 들어 예산을 10분의 1로 줄이거나 일관성 요구를 올린다. 달라지는 선택과 그 이유를 비교한다.
3. 설계에서 고른 패턴 하나를 [Spring Lab](../spring-lab/README.md)에 작게 구현하고 경계 조건을 재현한다. 속도 제한, 멱등성 키, 캐시 스탬피드 방지 중에서 고른다.
4. 장애 시나리오를 정하고 시스템의 반응을 설명한다. 캐시 전체 소실, 복제 지연 급증, 큐 적체 중에서 고른다. 어떤 기능이 먼저 느려지고 무엇을 끌 수 있는지 적는다.

## 스스로 설명할 질문

- 이 시스템은 읽기와 쓰기 중 어느 쪽이 먼저 한계에 닿는가? 그 근거가 되는 수치는 무엇인가?
- 캐시를 넣으면 일관성은 어떻게 나빠지는가? 허용 범위는 누가 정하는가?
- 같은 요청이 두 번 도착해도 안전한가? 어느 계층에서 보장하는가?
- 샤딩 키를 잘못 고르면 어떤 증상이 먼저 나타나는가?
- 의존하는 외부 시스템이 느려지기만 하고 죽지는 않을 때 무슨 일이 생기는가?

## 완료 기준

- [ ] 개략 계산으로 초당 요청 수, 저장 용량, 대역폭을 산출하고 가정한 값을 명시한다.
- [ ] 구성도와 데이터 흐름을 그림으로 남기고 각 구성 요소의 책임을 설명한다.
- [ ] 설계 대안을 최소 두 가지 비교하고 지연시간, 운영 부담, 일관성 측면의 비용을 제시한다.
- [ ] 병목 하나를 지목하고 그것이 먼저 한계에 닿는 이유를 수치로 설명한다.
- [ ] 패턴 하나를 코드로 구현하고 실패 또는 경계 조건을 최소 하나 재현한다.
- [ ] 적용 한계와 남은 질문을 기록한다.

개념 체크는 자신의 말로 설명하고 예제에서 확인했을 때 표시한다. 문서나 영상을 본 것만으로 완료 처리하지 않는다.
