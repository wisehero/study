# 부록 설계 질문 목록

쇼핑몰 적립금을 설계하면서 판단이 갈린 지점을 질문으로 모았다. 질문 번호는 공부하면서 쓴 번호를 그대로 따른다. **답은 접어 두었으니 먼저 스스로 판단해 보고 펼쳐서 비교한다.** 각 결론의 근거와 트레이드오프는 연결된 문서에 있다.

- [1부 적립금 원장과 동시 사용](01-적립금-원장과-동시-사용.md): Q1 ~ Q7
- [2부 소멸과 정합성 검증](02-소멸과-정합성-검증.md): Q8 ~ Q13

**공통 상황:** 구매를 확정하면 결제 금액의 1%를 적립하고, 리뷰와 이벤트로도 적립한다. 결제할 때 1원 단위로 쓰고, 적립 후 1년이 지나면 소멸한다. 주문을 취소하면 쓴 적립금은 돌려주고 받은 적립금은 회수한다.

## 1부 원장과 동시 사용

### Q1. 회원 테이블에 `point_balance` 컬럼 하나만 두면 안 되나요?

적립할 때 더하고 사용할 때 빼면 잔액은 바로 나온다. 위 요구사항 중 이 방식으로 처리할 수 없거나 처리하기 어려운 것은?

::: details 답과 결론
- 답: 적립과 사용 이력을 알 수 없다.
- 결론: 이력만이라면 이력 테이블을 옆에 붙여 풀 수 있다. 더 큰 문제는 잔액이 하나로 합쳐져 언제 적립된 적립금인지 모른다는 것이다. 그래서 유효기간 소멸, 취소 환원, 적립 회수를 처리하기 어렵다. → [잔액 숫자 하나로는 부족하다](01-적립금-원장과-동시-사용.md#_1-잔액-숫자-하나로는-부족하다)
:::

### Q2. 이력 테이블이 있으면 소멸 금액을 계산할 수 있나요?

3/1에 1,000원, 6/1에 1,000원을 적립하고 7/1에 1,500원을 썼다. 2027-03-01과 2027-06-01에 각각 소멸할 금액은? 그 답을 내려면 어떤 규칙이 필요한가?

::: details 답과 결론
- 답: 알 수 없다. 만료 기간이 있어야 한다.
- 결론: 만료일은 이 예제에서 `created_at + 1년`으로 계산할 수 있다. 정말 빠진 것은 사용 순서 규칙이다. 만료 임박 순으로 쓰면 0원과 500원, 최근 적립분부터 쓰면 500원과 0원이 소멸한다. 만료 임박 순을 고르고, 유효기간이 적립 건마다 다를 수 있으니 `expires_at`도 저장한다. → [이력 테이블을 붙여도 소멸 금액은 바로 나오지 않는다](01-적립금-원장과-동시-사용.md#이력-테이블을-붙여도-소멸-금액은-바로-나오지-않는다)
:::

### Q3. 매번 다시 계산하지 않으려면 무엇을 저장해야 하나요?

각 적립 건에 지금 얼마가 남았는지 바로 알려면 어떤 테이블이 필요한가? 사용 1건이 적립 여러 건에 걸치면 어떻게 기록하는가?

::: details 답과 결론
- 답: 원장 테이블 하나와, 잔여 포인트와 만료일을 기록하는 테이블이 따로 있어야 한다.
- 결론: 맞다. 원장(`point_transaction`)과 적립 건(`point_earning`)을 나눈다. 여기에 어느 적립 건에서 얼마를 뺐는지 기록하는 사용 상세(`point_usage_detail`)가 더 필요하다. 사용 상세가 없으면 취소할 때 어느 적립 건에 돌려줄지 모른다. → [원장과 적립 건 나누기](01-적립금-원장과-동시-사용.md#_2-원장과-적립-건-나누기)
:::

### Q4. 취소로 돌려준 적립금의 만료일은 언제로 하나요?

7/1에 1,500원을 쓴 주문을 7/5에 취소하면 각 테이블에서 무엇이 바뀌는가? 2027-04-01에 취소해서 3월분의 원래 만료일이 이미 지났다면?

::: details 답과 결론
- 답: 원장에 다시 쌓고 적립 건의 잔여분을 되돌린다. 만료일이 지난 경우는 모르겠다.
- 결론: 원장과 사용 상세는 고치거나 지우지 않고 취소 행을 새로 쌓는다. 취소가 두 번 처리되지 않게 원래 사용 거래 기준으로 유니크 제약을 건다. 만료일이 지난 경우는 정책 문제다. 원래 만료일 유지는 민원, 새 1년 부여는 만료 연장 악용이 생기므로, 만료된 분만 짧은 기간으로 재발급한다. 어느 정책이든 사용 상세가 있어야 구현할 수 있다. → [사용 취소](01-적립금-원장과-동시-사용.md#_3-사용-취소)
:::

### Q5. 받은 적립금을 이미 썼는데 원래 주문이 반품되면 어떻게 하나요?

구매 확정으로 받은 1,000원을 다른 주문에 모두 쓴 뒤 원래 주문이 반품됐다. 회수할 1,000원이 남아 있지 않다.

::: details 답과 결론
- 답: 회사가 손해를 감수할지 고객에게 부담시킬지 두 가지뿐이지 않나. 아니면 회수할 금액을 기록해 두고 나중에 리뷰, 이벤트, 구매 적립에서 메꾼다.
- 결론: 기록 후 상계는 맞는 방법이다. 다만 회수할 시점을 고르는 문제로 보면 선택지가 더 있다. 적립 시점 늦추기 → 환불 금액에서 빼기 → 미회수 기록 후 상계 → 손실 처리 순서로 겹쳐 쓴다. 미회수 금액은 마이너스 잔액이 아니라 별도 회수 대기 테이블에 둔다. → [적립 회수](01-적립금-원장과-동시-사용.md#_4-적립-회수)
:::

### Q6. 같은 회원이 두 결제를 동시에 하면 어떻게 되나요?

잔액 1,000원인 회원이 탭 두 개에서 각각 800원을 쓰는 결제를 거의 동시에 눌렀다. 무엇을 어디에 걸어 막는가?

::: details 답과 결론
- 답: 800원을 두 번 쓸 수 있다. 락을 쓴다.
- 결론: 맞다. 잠금 대상은 적립 건 여러 행보다 회원 잔액 1행이 낫다. 잠그는 지점이 하나라 데드락이 없다. 비관적 락이나 조건부 UPDATE로 확인과 차감을 원자적으로 한다. 다만 락은 버튼 두 번 클릭 같은 차례로 오는 중복 요청은 막지 못하므로, `(order_id, type)` 유니크 제약으로 멱등성을 함께 보장한다. → [동시 사용과 중복 요청](01-적립금-원장과-동시-사용.md#_5-동시-사용과-중복-요청)
:::

### Q7. 적립금과 카드로 나눠 결제하다가 중간에 실패하면 어떻게 하나요?

적립금 1,000원과 카드 29,000원으로 결제한다. 무엇을 먼저 하는가? 한쪽만 성공하면 어떻게 되돌리는가? 회원 잔액 락을 잡은 채 PG를 호출해도 되는가?

::: details 답과 결론
- 답: 적립금 차감을 먼저 한다. 카드 승인을 먼저 하면 돈은 빠져나갔는데 적립금이 부족해 롤백될 수 있다. 실패하면 재시도나 보상 트랜잭션을 쓴다. 락을 잡은 채 PG를 호출할 수는 있지만 트랜잭션을 너무 길게 잡아 위험할 수 있다.
- 결론: 순서와 이유가 맞다. 내부에서 싸게 되돌릴 수 있는 작업을 먼저 한다. 락을 잡은 채 PG를 호출하면 PG 지연이 커넥션 고갈로 번지고, 묶어도 PG 승인은 롤백되지 않는다. 적립금 차감을 먼저 커밋하고 PG는 트랜잭션 밖에서 호출한다. PG 응답이 없으면 실패로 단정하지 말고 조회 API로 확인한다. 카드 승인은 PG가 멱등성 키를 지원할 때만 재시도한다. → [적립금과 카드 복합 결제](01-적립금-원장과-동시-사용.md#_6-적립금과-카드-복합-결제)
:::

## 2부 소멸과 정합성 검증

**추가 상황:** 회원 1,000만 명, 평소 하루 소멸 대상은 약 12만 건이고 작년 이벤트 날의 적립 때문에 올해 그날은 약 120만 건이다. 소멸은 매일 0시에 처리하고 새벽에도 결제가 들어온다.

### Q8. 소멸을 SQL 한 문장으로 끝내면 안 되나요?

`UPDATE point_earning SET remaining_amount = 0 WHERE expires_at <= NOW() AND remaining_amount > 0` 하나로 끝내면 데이터 측면에서 무엇이 빠지는가? 120만 건을 한 트랜잭션으로 처리하면 운영 측면에서 어떤 문제가 생기는가?

::: details 답과 결론
- 답: 건수가 너무 많으면 오래 걸려서 다른 작업에 문제가 생길 것 같다. 락을 걸고 진행해야 한다.
- 결론: 운영 측면은 맞다. `UPDATE`가 120만 행의 락을 트랜잭션이 끝날 때까지 쥐어 새벽 결제가 막히고, 실패하면 전부 다시 해야 하며, 복제 지연이 생긴다. 데이터 측면에서는 원장의 `EXPIRE` 거래, 거래 상세, 회원 잔액이 빠진다. 소멸도 거래로 다루고, 회원 1명 = 트랜잭션 1개로 잘게 나눈다. → [소멸을 한 문장으로 끝내면](02-소멸과-정합성-검증.md#_1-소멸을-한-문장으로-끝내면)
:::

### Q9. 배치가 아직 처리하지 않은 만료 적립금은 쓸 수 있나요?

배치가 1시간 걸린다. 0시 30분에 아직 처리되지 않은 회원이 결제한다. 쓰게 두면 어떤 문제가 있고, 무엇을 바꿔야 하는가? 23:59:59에 시작해 00:00:01에 커밋된 결제는?

::: details 답과 결론
- 답: 만료된 것을 쓸 수 있어 회사가 손해를 본다. 사용 가능 포인트를 만료일 기준으로 집계해야 한다. 시작 시점의 스냅샷으로 판단하는 것이 맞다.
- 결론: 셋 다 방향이 맞다. 손해보다 큰 문제는 배치 순서에 따라 회원마다 결과가 다르다는 것이다. 만료일로 거르면 1부의 조건부 UPDATE가 틀리므로, 결제할 때 그 회원의 만료분을 먼저 소멸시키고 차감한다. 시작 시점은 서버가 요청을 받은 시각으로 한 번만 정해 `base_at`에 남긴다. → [배치가 처리하기 전의 만료 적립금](02-소멸과-정합성-검증.md#_2-배치가-처리하기-전의-만료-적립금)
:::

### Q10. 원장, 적립 건, 회원 잔액이 서로 맞는지 어떻게 확인하나요?

세 값이 어긋날 수 있는 경로는? 회원 1,000만 명을 매일 전부 비교해야 하는가?

::: details 답과 결론
- 답: (ERD를 함께 그린 뒤) 적립이나 차감이 생겼을 때 `balance`를 언제 갱신하는지 모르겠다. 다 썼거나 만료된 적립 건은 집계에서 뺀다.
- 결론: `balance`는 거래와 같은 트랜잭션 안에서, 잔액을 맨 처음 잠그고 맨 마지막에 갱신한다. 그래서 정상 흐름에서는 어긋나지 않고, 규칙을 빼먹은 기능, DB 직접 수정, 저장소 분리, 빠진 거래 유형에서 어긋난다. 닫힌 적립 건을 빼면 잘못 닫힌 건을 놓치므로, 기준을 "바뀌었는가"로 잡아 오늘 거래가 생긴 회원만 매일 검사하고 전체는 매달 검사한다. → [세 값이 맞는지 검증하기](02-소멸과-정합성-검증.md#_3-세-값이-맞는지-검증하기)
:::

### Q11. 어긋난 것을 찾으면 무엇을 기준으로 고치나요?

`balance`와 적립 건 합계는 5,000원, 원장 합계는 4,200원이다. 무엇을 진실로 믿고, `UPDATE`로 바로 맞춰도 되는가?

::: details 답과 결론
- 답: 원장이 단일 진실 원천이 되어야 한다. 고치는 방법은 모르겠다.
- 결론: 원장이 진실이 맞다. 다만 숫자만으로는 원장 누락인지 기록 없는 변경인지 모르므로 먼저 조사한다. `UPDATE`는 원인과 같은 "기록 없는 변경"이라 쓰지 않고, 원장에 `ADJUST` 보정 거래를 쌓는다. 부당한 변경이었다면 일어난 일을 먼저 기록하고 되돌린다. → [어긋났을 때 고치기](02-소멸과-정합성-검증.md#_4-어긋났을-때-고치기)
:::

### Q12. 지울 수 없는 원장이 계속 쌓이면 어떻게 하나요?

1년에 원장 3.65억 행, 상세 7.3억 행이 쌓인다. 무엇이 먼저 느려지고, 오래된 원장을 옮긴다면 기준과 옮기면 안 되는 것은?

::: details 답과 결론
- 답: 조회가 느려질 것이다. 날짜 기준으로 옮긴다. 옮기면 안 되는 것이 따로 있는지는 모르겠다.
- 결론: 인덱스로 몇 행만 찾는 조회는 크게 느려지지 않고, 회원의 원장 전체를 더하는 검증과 운영 작업이 먼저 느려진다. 날짜 기준이 맞지만 아직 취소될 수 있는 사용, 열린 적립 건, 남은 회수 대기, 조사 중인 거래는 옮기지 않는다. 옮기기 전에 이월 잔액을 남겨 검증식을 유지한다. → [원장 보관](02-소멸과-정합성-검증.md#_5-원장-보관)
:::

### Q13. "30일 안에 소멸 예정인 적립금" 안내는 어떻게 만드나요?

화면 금액은 어떤 조회로 구하는가? 알림을 두 번 보내지 않으려면? 알림 뒤에 적립금을 써서 소멸 예정 금액이 줄면?

::: details 답과 결론
- 답: `balance`로 구한다. 금액은 그냥 줄어든다. 알림은 아웃박스로 관리한다.
- 결론: `balance`는 전체 잔액이라 적립 건의 `remaining_amount`를 만료일 범위로 더한다. 금액이 줄어도 고객에게 불리하지 않으니 "○월 ○일 기준"이라고 밝히면 된다. 더 조심할 것은 짧은 재발급 건이 안내에서 빠지는 경우라, 안내 여부를 적립 건마다 기록한다. 중복은 `(earning_id, notice_type)` 유니크 제약이 막고, 아웃박스는 빠짐없이 보내는 것을 보장한다. → [소멸 예정 안내](02-소멸과-정합성-검증.md#_6-소멸-예정-안내)
:::
