# 부록 설계 질문 목록

이커머스 OMS를 설계하면서 판단이 갈린 지점을 질문으로 모았다. 질문 번호는 설계 과정에서 쓴 번호를 그대로 따른다. Q6-2a(무엇을 비교하는가)는 Q6-2에 합쳤다. **답은 접어 두었으니 먼저 스스로 판단해 보고 펼쳐서 비교한다.** 각 결정의 근거와 트레이드오프는 연결된 설계 문서에 있다.

- [1단계 요구사항 정리](01-요구사항-정리.md): Q1 ~ Q9
- 미룬 비기능 요구: Q10 ~ Q15
- [3단계 상위 설계](02-상위-설계.md): Q16 ~ Q21

## 1단계 기능 요구

### Q1. 주문은 어디서 들어오나요?

자사몰 하나뿐인가, 외부 오픈마켓 여러 곳에서도 들어오는가? 들어온다면 OMS가 받는 방식은 푸시(웹훅)인가, 풀(주기적 조회)인가?

::: details 답과 결론
- 답: 쇼피파이, 메르카도리브레, 카페24, 틱톡샵 네 곳이다. 채널마다 주문 형식이 다르다. 기본은 웹훅이다.
- 결론: 채널별 어댑터가 채널 주문을 OMS 공통 주문 모델로 변환한다. 웹훅만 믿으면 유실, 중복, 순서 역전이 생긴다. → [주문 수집](01-요구사항-정리.md#_2-주문-수집)
:::

### Q2. 주문이 거치는 상태를 처음부터 끝까지 적고, 어디까지가 OMS의 책임인지 정해 주세요.

결제 승인을 OMS가 직접 하는가, 결과만 받는가? 배송 추적도 OMS가 하는가?

::: details 답과 결론
- 답: 주문 접수 → 결제 완료 → 배송 준비중 → 배송 중 → 배송완료 또는 구매확정. 책임 범위는 답하지 않았다.
- 보완 1: 채널이 결제를 받으므로 결제는 OMS의 책임이 아니다. OMS의 첫 상태는 결제가 끝난 주문의 수집이다.
- 보완 2: 창고가 여러 곳이므로 "배송 준비중"을 재고 할당 → 출고 지시 → 출고 완료로 쪼갠다. 취소 가능 여부가 이 경계에서 갈린다.
- 보완 3: 부분 취소를 허용하므로 상태는 주문이 아니라 라인 단위로 둔다.
- 보완 4: 배송완료와 구매확정은 둘 중 하나가 아니라 순서다.
- 결론: [OMS의 책임 경계](01-요구사항-정리.md#_1-oms의-책임-경계), [주문 상태](01-요구사항-정리.md#_3-주문-상태)
:::

### Q3. 재고의 원천은 어디인가요?

OMS가 재고 수량을 직접 들고 있는가, WMS가 원천이고 OMS는 받아 보기만 하는가? 출고 창고는 몇 곳인가?

::: details 답과 결론
- 답: 재고의 원천은 WMS다. 창고는 최대 3곳이다.
- 결론: 같은 재고를 채널 4곳이 동시에 판다는 점이 설계의 핵심 쟁점이 된다. → Q7
:::

### Q4. 취소·반품·교환은 이번 범위에 넣을까요?

넣는다면 부분 취소도 허용하는가? 출고 이후 취소는 어떻게 처리하는가?

::: details 답과 결론
- 답: 넣는다. 부분 취소도 허용한다. 출고 이후 취소는 도메인 지식이 부족해 답하지 못했다.
- 결론: 출고 지시 전에는 바로 취소, 출고 지시 후 출고 전에는 출고 중지 요청(실패 가능), 출고 후에는 반품으로 전환한다. 환불은 채널이 실행한다. → [취소와 반품](01-요구사항-정리.md#_6-취소와-반품)
:::

### Q5. OMS를 쓰는 주체는 누구인가요?

고객의 주문 조회, 운영자 백오피스, 외부 시스템(마켓·창고·택배사) API 중 어디까지 지원하는가?

::: details 답과 결론
- 답: 고객의 주문 조회와 운영자 백오피스.
- 보완: OMS는 채널에도 결과를 되돌려 보내야 한다. 송장번호를 채널에 등록해야 고객이 채널에서 배송을 조회할 수 있다.
:::

### Q6. 웹훅 유실은 어떻게 메울까요?

(a) 유실을 감수한다, (b) 주기적으로 채널 API를 조회해 보정한다, (c) 다른 방법.

::: details 답과 결론
- 답: 메르카도리브레는 1시간 동안 8회 재시도한다고 하지만, (b)로 두 겹을 둔다.
- 결론: 웹훅은 빠른 경로, 폴링은 보정 경로다. 대신 같은 주문이 여러 번 도착하는 것이 기본 전제가 된다. 재시도 정책은 공식 문서로 확인해야 한다. → [웹훅과 폴링의 두 겹 수집](01-요구사항-정리.md#웹훅과-폴링의-두-겹-수집)
:::

### Q6-1. 중복은 무엇으로 판정하나요?

채널이 다르면 주문번호가 겹칠 수 있다.

::: details 답과 결론
- 답: 채널과 주문번호에 함께 유니크 제약을 건다.
- 보완: 한 채널에 판매자 계정(스토어)이 여러 개일 수 있으므로 키는 `(채널, 스토어, 채널 주문번호)`다.
:::

### Q6-2. 이미 있는 주문이 상태가 바뀐 채로 다시 들어오면 어떻게 하나요?

오래된 정보가 새 정보를 덮어쓰지 않게 하려면 무엇을 비교해야 하는가?

::: details 답과 결론
- 답: 주문 원장은 덮어쓰고 감사 테이블에 이력을 남긴다. 이후 append-only로 바꿨다.
- 보완: append-only로 쌓아도 "마지막에 들어온 행"을 현재 상태로 보면 늦게 처리된 폴링 결과가 최신이 된다. 문제는 도착 순서를 최신 순서로 착각한 데 있다.
- 결론: 채널 원본은 append-only로 쌓고, OMS 주문은 `channel_updated_at`이 마지막으로 반영한 값보다 새로울 때만 갱신한다. 뒤로 가는 상태 전이는 막는다. → [저장 구조](01-요구사항-정리.md#저장-구조), [공통 원칙](01-요구사항-정리.md#_7-공통-원칙)
:::

### Q6-2b. 채널이 준 원본과 OMS의 주문을 한 테이블에 둘까요, 나눌까요?

채널 데이터로 주문 전체를 덮어쓰면 OMS가 만든 정보(할당한 창고, 출고 지시 여부, 송장번호)가 지워질 수 있다.

::: details 답과 결론
- 결론: 나눈다. 채널 원본 이력과 OMS 주문을 따로 둔다. → [저장 구조](01-요구사항-정리.md#저장-구조)
:::

### Q6-3. 폴링은 얼마나 자주, 어떤 범위를 조회하나요?

폴링 주기는 웹훅이 유실됐을 때 수집이 늦어지는 최악의 시간이다. 너무 자주 돌리면 채널 API의 호출 한도에 걸린다.

::: details 답과 결론
- 답: 30초마다 조회한다. 범위는 답하지 못했다.
- 보완: 30초면 스토어 하나당 하루 2,880회다. "최근 30초"만 조회하면 시계 차이와 채널 반영 지연 때문에 경계의 주문이 빠질 수 있다.
- 정리: 처리한 주문 중 가장 큰 `channel_updated_at`을 워터마크로 두고, `워터마크 - 10분`부터 겹쳐서 조회한다. 겹쳐 들어온 주문은 멱등성 덕분에 결과가 같다. 웹훅이 평소 지연을 책임지므로 폴링은 5분 주기로 늘린다.
- 짚을 점: 비싼 지연은 주문 생성이 아니라 **취소**다. 그래서 출고 지시 직전에 채널 상태를 한 번 더 확인한다.
- 결론: [폴링 조회 범위](01-요구사항-정리.md#폴링-조회-범위), [출고 지시 직전 재확인](01-요구사항-정리.md#출고-지시-직전-재확인)
:::

### Q7. 채널별 판매 가능 수량은 누가, 어떻게 정하나요?

실재고 10개를 채널 4곳에서 동시에 판다. (a) 모든 채널에 같은 수량, (b) 채널별로 나눠 배정, (c) 같은 수량에서 안전 재고를 빼고 알린다.

::: details Q7-1. 세 방식에서 각각 어떤 사고가 나나요?
- 답: (a)는 무조건 초과 판매, (b)와 (c)는 기회 손실.
- 보완: (a)는 무조건이 아니라 재고가 바닥에 가까울 때 동기화 전에 여러 채널에서 팔리면 초과 판매가 난다. (c)는 초과 판매 확률을 줄이는 대신 안전 재고만큼 기회 손실을 지불하는 절충이고, 가장 흔한 방식이다.
:::

::: details Q7-2. 한 채널에서 팔린 뒤 나머지 채널 수량이 바뀌기까지 무슨 일이 생기나요?
- 답: 무조건 오버셀이 난다.
- 보완: 동기화 시간 동안 팔린 양이 남은 수량보다 많을 때만 난다. 그래서 `안전 재고 ≈ 판매 속도 × 동기화 시간`으로 계산할 수 있다.
:::

::: details Q7-3. 채널에 알려 줄 판매 가능 수량은 어떻게 계산하나요?
- 답: 예약(할당) 수량을 뺀 재고를 OMS가 계산해서 알린다. 정답.
- 결론: `WMS 가용 재고 − OMS 할당 수량 − 안전 재고` → [판매 가능 수량](01-요구사항-정리.md#판매-가능-수량)
:::

::: details Q7-4. 출고 순간 WMS 재고 차감과 할당 해제 중 하나가 먼저 반영되면?
- 답 1: 거래액이 우선이고 리드타임이 짧으면 초과 판매를, 아니면 보수적으로 기회 손실을 택한다. 기본은 기회 손실 쪽이다.
- 답 2: 트랜잭션 순서대로 되는 것 아닌가.
- 보완: 두 값은 서로 다른 시스템에 있어 한 트랜잭션으로 묶을 수 없다. OMS가 WMS 재고 사본을 들고, 출고 완료 이벤트를 받으면 한 트랜잭션에서 사본과 할당을 함께 줄인다. 출고 전에 찍힌 스냅샷이 늦게 오면 생성 시각을 비교해 버린다.
- 결론: [출고 순간의 경계](01-요구사항-정리.md#출고-순간의-경계)
:::

::: details Q7-5. 안전 재고는 어떻게 정하나요?
- 답: 상품별 판매 속도로 계산한다.
- 보완: 판매 이력이 없는 신상품과 프로모션 상품을 위해 최솟값을 둔다. `max(최소값, 판매 속도 × 동기화 시간)` → [안전 재고](01-요구사항-정리.md#안전-재고)
:::

::: details Q7-6. 그래도 초과 판매가 나면 어떻게 하나요?
- 답: 정책 결정의 문제다.
- 보완: 맞다. 정책은 사업이 정하고, 설계에서는 가정으로 명시하고 넘어간다. 다만 정책과 상관없이 시스템은 감지 시점, 보관 상태(`할당 보류`), 출고 기한 타이머, 결정 주체를 갖춰야 한다. → [초과 판매가 났을 때](01-요구사항-정리.md#초과-판매가-났을-때)
:::

### Q8. 재고 할당 시 창고 3곳 중 어디를 고를까요?

::: details Q8-1. 가장 가까운 창고인가, 재고가 가장 많은 창고인가?
- 답: 둘 다 좋은 선택지라 고민된다.
- 결론: 둘을 순서대로 쓴다. 한 창고에서 다 채울 수 있는 곳 중 가장 가까운 곳 → 없으면 분할 출고 건수가 가장 적은 조합 → 거리가 같으면 재고가 많은 곳. → [창고 선택](01-요구사항-정리.md#창고-선택-가정)
:::

::: details Q8-2. 한 창고에서 다 채울 수 없으면 분할 출고를 허용하나요?
- 답: 허용한다.
:::

## 3단계 상위 설계

### Q16. 웹훅을 받으면 바로 처리할까요, 받아 두고 나중에 처리할까요?

채널은 정해진 시간 안에 성공 응답이 없으면 재시도한다. 그런데 주문 처리에는 변환, 저장, 할당, 재고 재계산, 채널 갱신까지 할 일이 많다.

::: details 답과 결론
- 답: 비동기로 한다. 오픈마켓은 빠른 응답을 요구한다. 인박스에 쌓아 두고 변환해서 주문에 넣는다. 배송 도착일 보장에 따라 달라질 수 있다.
- 결론: 인박스 패턴이다. 폴링과 WMS 이벤트도 같은 인박스에 넣고, 인박스가 채널 원본 이력을 겸한다. → [인박스 패턴](02-상위-설계.md#인박스-패턴)
:::

### Q17. 같은 주문의 "생성"과 "취소"를 컨슈머 두 대가 동시에 처리하면?

::: details 답과 결론
- 답: Kafka 또는 SNS·SQS를 쓴다고 가정한다.
- 보완: 큐를 쓴다고 저절로 풀리지 않는다. 다른 파티션에 들어가면 여전히 동시에 처리된다.
- 결론: 주문 키로 묶어 같은 주문은 한 번에 하나씩 처리한다. 컨슈머는 서버가 아니라 컨슈머 인스턴스 단위이고, 컨슈머 안에서 스레드 풀로 넘기면 순서가 다시 깨진다. 최소 한 번 전달이라 멱등성은 여전히 필요하다. → [같은 주문은 한 번에 하나씩](02-상위-설계.md#같은-주문은-한-번에-하나씩)
:::

::: details Q17-1. 같은 주문의 메시지를 항상 같은 파티션에 넣으려면 키를 무엇으로 하나요?
- 정리: `(채널, 스토어, 채널 주문번호)`. Kafka는 파티션 키, SQS FIFO는 메시지 그룹 ID로 쓴다. OMS 내부 주문 ID는 웹훅이 처음 도착할 때 아직 없어서 쓸 수 없다.
:::

::: details 멱등키는 OMS가 만들어서 WMS로 주는 건가요? (사용자 질문)
- 결론: 키는 세 가지로 나뉜다. 주문 키(채널이 준 값, 순서용), 수신 메시지 ID(보낸 쪽이 준 값, 중복 수신용), 출고 지시 ID(OMS가 만듦, WMS 명령의 멱등키). 출고 지시 ID는 아웃박스에 저장할 때 한 번만 만든다. → [세 가지 키](02-상위-설계.md#세-가지-키)
:::

::: details 3PL WMS가 멱등키를 지원하지 않으면 어떻게 하나요?
- 결론: 외부 참조번호 필드를 멱등키처럼 쓰고, 결과를 모르는 실패만 조회 후 재전송하고, 주기적으로 대사하고, 필요하면 운영자에게 넘긴다. → [WMS가 멱등키를 지원하지 않을 때](02-상위-설계.md#wms가-멱등키를-지원하지-않을-때)
:::

### Q18. 다른 주문 두 개가 마지막 재고 1개를 동시에 할당하면?

주문 키로 묶는 방법이 여기서 왜 통하지 않는지도 생각한다.

::: details 답과 결론
- 답: 분산 락을 쓴다.
- 보완: 동작은 하지만 시스템이 하나 늘고, 락 만료 문제가 있다. 부딪히는 대상이 주문이 아니라 SKU라서 주문 키로는 못 막고, SKU로 파티션을 나누면 여러 상품 주문과 인기 상품 쏠림 문제가 생긴다.
- 결론: 판단을 UPDATE 조건에 넣어 DB가 판단하게 한다. 지켜야 할 데이터가 DB 한 곳에 있으면 락도 그 DB에서 건다. → [다른 주문이 같은 재고를 다툴 때](02-상위-설계.md#다른-주문이-같은-재고를-다툴-때)
:::

::: details Q18-1. 주문 하나에 상품 A, B가 있는데 A만 할당되고 B는 재고가 없으면?
- 답: B는 다른 WMS와 통신해 재고가 있는 곳을 찾는다. 끝내 없으면 A만 정상 결제되게 한다.
- 보완: 다른 창고 재고는 OMS DB의 재고 사본에서 찾는다. 할당 도중 WMS를 호출하면 느려지고 경쟁 조건이 돌아온다. 결제는 채널이 주문 전체로 끝냈으므로 "A만 결제"는 없고, B를 부분 취소하고 환불을 요청한다.
- 정리: 락 없이 계획 → 한 트랜잭션에서 조건부 UPDATE로 실행 → 충돌하면 롤백하고 재계획. A는 커밋하고 먼저 출고, B는 `할당 보류`. UPDATE는 `(SKU, 창고)` 순서로 정렬해 교착 상태를 막는다. → [상품이 여러 개인 주문](02-상위-설계.md#상품이-여러-개인-주문)
:::

### Q19. 멱등키가 없는 WMS에서 결과를 모를 때, 중복 출고와 출고 누락 중 어느 쪽이 더 나쁜가요?

::: details 답과 결론
- 답: 출고 누락이 더 나쁘다.
- 이유: 누락은 아무도 모르게 조용히 일어나 출고 기한 초과나 고객 문의로 드러나고, 중복은 대사나 재고 동기화로 흔적이 남는다.
- 결론: 결과를 모르면 조회 후 재전송하고, 대사로 중복을 피킹 전에 잡는다. 고가 상품이면 판단이 뒤집힐 수 있다. → [WMS가 멱등키를 지원하지 않을 때](02-상위-설계.md#wms가-멱등키를-지원하지-않을-때)
:::

### Q20. 판매 가능 수량이 바뀔 때마다 채널 4곳에 바로 보내면 호출 한도에 막힌다. 어떻게 할까요?

1초에 10건씩 팔리는 상품 하나로만 1초에 40번을 호출한다(가정).

::: details 답과 결론
- 답: 실시간이 아니라 주기적으로 보낸다.
- 보완: 모든 상품을 주기마다 보내면 낭비다. 바뀐 상품만 `(SKU, 채널)`별 최신 값으로 모아 두었다가 보낸다(병합). 품절에 가까우면 즉시 보내고, 채널별 속도 제한기를 거친다.
- 결론: [바뀐 것만 모아 최신 값 하나로 보낸다](02-상위-설계.md#바뀐-것만-모아-최신-값-하나로-보낸다)
:::

### Q21. 전송 주기 N초는 몇 초로 할까요?

N을 늘리면 호출은 줄지만 동기화 시간이 늘어 안전 재고가 커진다.

::: details 답과 결론
- 답: 수량이 많으면 덜 자주, 몇 개 없으면 빠르게 보낸다.
- 보완: 수량보다 `남은 수량 ÷ 판매 속도`, 즉 소진 예상 시간으로 판단한다. 100개 남아도 1초에 10개씩 팔리면 10초 뒤 품절이다.
- 결론: 소진 예상 시간에 따라 즉시 · 30초 · 5분(가정). → [소진 예상 시간에 따라 주기를 다르게](02-상위-설계.md#소진-예상-시간에-따라-주기를-다르게)
:::
