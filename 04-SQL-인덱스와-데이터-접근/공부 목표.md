# 공부 목표: SQL·인덱스와 데이터 접근

> 상태: 시작 전 · 작성일: 2026-09-09 · 목표 수준: Java·Spring 미들급 개발자의 독립적인 구현·검증·문제 해결

## 학습 목적

애플리케이션이 발생시키는 SQL과 DB 실행 계획을 이해하고, 데이터량 증가에 따른 성능 문제를 측정하여 개선한다.

**학습 우선순위:** 최우선 심화 주제다. 트랜잭션 학습과 병행한다. JPA 항목은 사용 시 필수로 다룬다.

## 학습 환경

- Java / Spring Boot 버전: 미정
- DB / 데이터 접근 기술: 미정
- 실습 코드 위치: 미정

현재 프로젝트의 기술과 버전을 적은 뒤 시작한다. 확인하지 않은 동작은 가정으로 표시하고 실습으로 검증한다.

## 핵심 개념별 목표

- [ ] **SQL과 데이터 모델**: 조인, 집계, 서브쿼리, NULL의 비교 규칙을 이해한다. 기본키·외래키·유니크 제약과 정규화의 목적을 설명한다.
- [ ] **인덱스**: 인덱스의 탐색 이점과 쓰기·저장 비용을 이해한다. 복합 인덱스의 컬럼 순서와 조회 조건·정렬 조건의 관계를 분석한다.
- [ ] **실행 계획**: DB의 조회·조인·정렬 방식을 보여주는 실행 계획을 읽고, 예상 행 수와 실제 처리량을 비교한다. 인덱스가 존재해도 사용되지 않을 수 있는 이유를 설명한다.
- [ ] **페이지네이션**: OFFSET 방식과 마지막 조회 키를 사용하는 커서 방식의 성능·사용성 차이를 이해한다. 정렬 값이 같을 때도 순서가 결정되도록 설계한다.
- [ ] **JPA의 객체 관리**: JPA를 사용할 경우 영속성 컨텍스트의 객체 관리, 변경 감지, flush와 commit의 차이, 지연 로딩의 실행 시점을 이해한다.
- [ ] **조회 수와 범위**: 목록 조회 후 항목별 추가 쿼리가 발생하는 N+1 문제를 찾는다. fetch join, 배치 조회, 필요한 필드만 조회하는 방식의 적용 조건을 비교한다.

## 실습 과제

1. 로컬 실습 DB에 주문·주문 항목·상품 데이터를 충분히 넣고 주문 목록 API의 SQL 수, 응답 시간, 반환 데이터량을 기록한다.
2. 조회 조건에 맞춘 인덱스를 추가하고 실행 계획과 처리 시간을 전후 비교한다. 인덱스가 유리하지 않은 조회 조건도 확인한다.
3. JPA 사용 시 N+1 문제를 재현하고 해결한다. 컬렉션 fetch join과 페이지네이션을 함께 적용할 때 실행 SQL과 메모리 사용을 확인한다.
4. 정렬 값이 같은 데이터와 페이지 사이에 새 데이터가 추가되는 상황에서 페이지 조회 결과를 확인한다.

## 스스로 설명할 질문

- 인덱스가 있는데도 조회가 느린 이유를 무엇부터 확인하는가?
- flush가 실행되면 트랜잭션이 커밋된 것인가?
- 주문 목록 20건 조회에 SQL 21개가 실행된다면 어디를 확인하는가?

## 완료 기준

- [ ] 동일한 측정 조건에서 개선 전후 결과를 기록한다.
- [ ] 조회 최적화가 쓰기 비용, 페이지 정확성, 메모리에 미치는 영향을 설명한다.
- [ ] 실패 또는 경계 조건을 최소 하나 직접 재현하고 결과를 기록한다.
