# 공부 목표: 상품 진열·정렬과 조회

> 상태: 시작 전 · 작성일: 2026-09-09 · 상위 주제: 전시 도메인

## 학습 목적

상품 원본과 전시 배치의 책임을 구분하고, 운영자의 순서 변경과 고객의 목록 조회가 일관된 규칙으로 동작하도록 한다.

## 핵심 개념별 목표

- [ ] 상품은 이름·가격·판매 상태 같은 원본 정보를 가진다. 진열 항목은 어떤 전시 구역에 어떤 상품을 어떤 순서로 보여줄지 연결하는 정보다.
- [ ] 판매 가능 여부, 품절 여부, 고객에게 공개 가능한 상태는 서로 다른 판단이다. 전시 가능과 구매 가능을 분리한다.
- [ ] 순서 변경은 여러 항목을 함께 바꾸는 작업이다. 관리 화면에서 읽은 이후 다른 관리자가 변경했는지 확인하는 버전 검증을 이해한다.
- [ ] 안정적인 정렬은 같은 순위의 항목에도 고유 식별자 같은 보조 기준을 적용하는 것이다. 페이지 사이에 데이터가 바뀌는 문제까지 모두 해결하는 것은 아니다.

## 초기 실습 정책

다음은 연습을 구체화하기 위해 선택한 정책이다. 실제 회사의 현재 동작이나 모든 쇼핑몰의 공통 규칙을 뜻하지 않는다. 정책을 바꾸면 이유와 영향받는 테스트를 함께 기록한다.

- 초기 실습은 수동 상품 진열로 시작한다. 같은 구역에 동일 상품을 중복 등록할 수 없지만 다른 구역에는 등록할 수 있다.
- 공개·판매 중인 상품은 표시한다. 품절 상품은 품절 표시와 함께 노출하고, 비공개·판매 중지·삭제 상품은 숨긴다. 구매 직전에는 주문 영역에서 가격·재고를 다시 검증한다.
- 진열 순서 변경은 하나의 트랜잭션으로 반영한다. 구역의 편집 버전이 일치하지 않으면 충돌로 응답하고 재조회를 요구한다.
- 목록은 진열 순위와 진열 항목 ID 순으로 정렬한다. 초기에는 OFFSET 페이지네이션을 사용하며 조회 중 편집에 따른 중복·누락 가능성을 명시한다.
- 품절·비공개 필터를 어느 단계에서 적용하는지 정의한다. 페이지 크기를 맞추기 위해 조회 후 제거만 하는 방식의 빈 페이지 문제를 확인한다.

## 실습 과제

1. 상품과 진열 항목을 분리한 모델 및 관리자 등록·순서 변경, 고객 구역별 목록 API를 설계한다.
2. 관리자 두 명이 같은 버전으로 서로 다른 순서를 저장할 때 한 변경이 조용히 덮어써지지 않도록 검증한다.
3. 같은 순위, 비공개 상품, 품절 상품, 비어 있는 구역의 응답 예시와 테스트를 작성한다.
4. 상품 목록을 충분히 늘려 SQL 수·반환 필드·실행 계획을 확인한다. 상품별 추가 조회와 불필요한 대용량 데이터 조회를 개선한다.
5. 페이지 사이에 진열 순서를 변경해 결과를 관찰한다. 커서 방식 또는 전시 버전 고정 방식이 필요한 조건과 비용을 비교한다.

## 스스로 설명할 질문

- 상품에 진열 순서 컬럼 하나만 두면 여러 구역에서 어떤 문제가 생기는가?
- 낙관적 락을 어느 객체에 적용해야 구역 전체의 편집 충돌을 감지할 수 있는가?
- 커서 페이지네이션을 사용하면 정렬 키 변경 중에도 중복·누락이 완전히 사라지는가?
- 상품 서비스 장애로 응답이 없을 때 빈 목록을 정상 결과로 반환해도 되는가?

## 완료 기준

- [ ] 상품 원본과 전시 배치의 책임을 모델과 API로 설명한다.
- [ ] 동시 순서 변경에서 원자성과 충돌 처리를 검증한다.
- [ ] 품절·비공개·빈 목록·정렬 동률의 정책을 테스트로 고정한다.
- [ ] 목록 SQL과 실행 계획을 근거로 개선 전후를 기록한다.
- [ ] 설계 이유, 실패 또는 경계 조건, 검증 결과를 학습 노트와 실습 기록에 남긴다.
