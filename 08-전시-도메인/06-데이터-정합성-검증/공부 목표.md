# 공부 목표: 전시 데이터 정합성 검증

> 상태: 시작 전 · 작성일: 2026-09-09 · 상위 주제: 전시 도메인

## 학습 목적

전시 읽기 모델·캐시가 원본 데이터와 시간이 지나며 벌어지는 상황(드리프트)을 감지하고 재동기화하는 방법을 설계한다. 05번 주제가 "정상적으로 반영하는 흐름"을 다룬다면, 이 주제는 "그 흐름이 실패했을 때 어떻게 알아채는가"를 다룬다.

## 핵심 개념별 목표

- [ ] 드리프트는 이벤트 유실, 배치 실패, 배포 중 경합 등으로 읽기 모델·캐시가 원본과 어긋난 상태다. 정상적인 짧은 반영 지연과 장기간 이어지는 드리프트를 구분한다.
- [ ] 검증 방식은 전수 비교, 샘플링 비교, 체크섬(해시) 비교로 나뉜다. 각각의 정확도와 실행 비용(시간·리소스)을 비교한다.
- [ ] 검증은 정기 배치로 돌리거나, 이벤트 발행 실패 같은 신호를 받았을 때 즉시 트리거할 수 있다.
- [ ] 불일치 발견 시 자동 재동기화와 알림 후 수동 확인 중 어떤 것을 선택할지는 원본이 오히려 잘못된 상태일 가능성과 재동기화의 부작용을 함께 고려해 정한다.
- [ ] 불일치 건수·비율을 지표로 노출하고 임계치를 넘으면 경보한다. 어떤 필드가 자주 어긋나는지 원인별로 분류한다.
- [ ] 근본 원인 추적을 위해 어떤 이벤트가 유실됐는지, 어떤 배치가 실패했는지 되짚어볼 수 있는 로그와 이벤트 이력을 남긴다.

## 초기 실습 정책

다음은 연습을 구체화하기 위해 선택한 정책이다. 실제 회사의 현재 동작이나 모든 쇼핑몰의 공통 규칙을 뜻하지 않는다. 정책을 바꾸면 이유와 영향받는 테스트를 함께 기록한다.

- 검증 배치는 원본과 읽기 모델의 핵심 필드(가격, 판매 상태, 공개 여부)만 우선 비교하는 것으로 범위를 좁혀 시작한다.
- 방금 저장되어 아직 반영되지 않은 정상 지연을 오탐으로 잡지 않도록, 최소 유예 시간(예: 1분) 이내의 불일치는 재검증 대상으로만 표시하고 즉시 경보하지 않는다.
- 자동 재동기화는 읽기 모델 쪽만 원본 값으로 덮어쓰는 방향으로 제한한다. 원본 자체가 의심되는 경우는 자동 처리하지 않고 알림으로만 남긴다.
- 불일치 이력은 언제, 어떤 상품, 어떤 필드가 어긋났는지 기록해 반복되는 원인을 나중에 분석할 수 있게 한다.

## 실습 과제

1. 이벤트 소비자를 일시 중단시켜 원본과 읽기 모델 사이에 의도적으로 불일치를 만들고, 정기 검증 배치로 이를 탐지한다.
2. 체크섬 비교와 전수 필드 비교 두 방식으로 같은 불일치를 각각 탐지해보고 실행 시간과 리소스 사용량을 비교한다.
3. 유예 시간을 도입해, 저장 직후의 정상 지연을 오탐으로 잡지 않으면서도 실제 드리프트는 놓치지 않는지 검증한다.
4. 불일치 발견 시 자동 재동기화를 적용하고, 재동기화 이력과 지표(건수·비율)가 정확히 기록되는지 확인한다.

## 스스로 설명할 질문

- 정기 검증 배치가 막 저장 중인 데이터를 오탐으로 잡으면 어떻게 구분하는가?
- 체크섬 비교로 불일치를 발견했지만 어떤 필드가 다른지 알 수 없다면 다음에 무엇을 확인하는가?
- 자동 재동기화를 걸었는데 원본 자체가 잘못된 값이라면 어떤 문제가 생기는가?

## 완료 기준

- [ ] 정상 지연과 드리프트를 구분하는 기준을 설명한다.
- [ ] 검증 방식(전수·샘플링·체크섬) 중 하나 이상을 구현하고 비용을 비교한다.
- [ ] 불일치를 재현하고 탐지·재동기화 흐름을 검증한다.
- [ ] 설계 이유, 실패 또는 경계 조건, 검증 결과를 학습 노트와 실습 기록에 남긴다.
